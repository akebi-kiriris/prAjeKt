# Phase 10.2 後端契約收斂實作整理

> 更新日期：2026-06-15  
> 目的：整理這一輪 Phase 10.2 實際已完成的後端契約收斂工作，方便後續逐項確認。

## 1. 這一輪 10.2 實際完成了什麼

這一輪不是只補規劃文件，而是已經把一批後端 request contract 從 blueprint 內抽出，開始收斂到共用契約層，並讓 blueprint / service / tool 盡量共用同一組 Pydantic schema。

本輪完成的核心方向有四個：

1. 補齊後端契約索引與 10.2 規劃文件
2. 把高風險模組的 request schema 從 blueprint 內抽離
3. 補一層 shared field / validator，減少各模組重複驗證
4. 讓部分 service 主路徑也改用同一套 contract 驗證，而不是只在 route 層驗一次

---

本輪新增：

- `backend/contracts/shared_fields.py`
- `backend/contracts/auth_contracts.py`
- `backend/contracts/profile_contracts.py`
- `backend/contracts/knowledge_contracts.py`
- `backend/contracts/todo_contracts.py`

這些檔案的角色不是商業邏輯，而是把欄位型別、必填規則、正規化與單純跨欄位檢查集中起來。

## 3. 既有契約檔案的收斂

本輪延伸調整：

- `backend/contracts/task_contracts.py`
- `backend/contracts/timeline_contracts.py`
- `backend/contracts/tool_inputs.py`
- `backend/contracts/README.md`

重點如下：

- `task_contracts.py`
  - 補上 task route 會用到的 request schema
  - 讓 create / update / member / comment / subtask / status 等 payload 有明確契約入口
- `timeline_contracts.py`
  - 補上 create / update / remark / member / AI 產 task / batch create task 等 request schema
  - 讓 timeline 主線不再只靠 blueprint 內嵌 payload 類別
- `tool_inputs.py`
  - 改成重用 task / timeline 的 request contract
  - 避免 tool contract 再各自維護一套近似但不同的欄位規則
- `shared_fields.py`
  - 集中可共用的 enum、字串清理、正整數、日期、priority、status 驗證邏輯

## 4. Blueprint 端做了哪些調整

以下 blueprint 已改為優先使用抽出的 contract：

- `backend/blueprints/auth.py`
- `backend/blueprints/profile.py`
- `backend/blueprints/tasks.py`
- `backend/blueprints/timelines.py`
- `backend/blueprints/knowledge.py`
- `backend/blueprints/todos.py`
- `backend/blueprints/groups.py`

這些調整的共同方向是：

1. blueprint 保留 HTTP 入口責任
2. blueprint 保留 `validate_payload_or_400(...)` 與錯誤映射
3. blueprint 盡量不再自己持有大量 domain request schema

也就是說，`blueprints/validation.py` 現在比較像 HTTP 驗證基礎設施，而不是 schema 倉庫。

## 5. Service 端做了哪些調整

以下 service 主路徑也已開始改用同一批 contract：

- `backend/services/auth_service.py`
- `backend/services/profile_service.py`
- `backend/services/task_service.py`
- `backend/services/timeline_service.py`
- `backend/services/todo_service.py`
- `backend/services/group_service.py`

這一層的重點不是把 service 變成第二個 route，而是補強：

1. service 真正依賴的輸入型別有明確契約
2. 即使未來不是從 HTTP route 進來，也不會完全失去基本資料驗證
3. blueprint / service / tool 對同一個 domain 的輸入規則比較不會分叉

## 8. 這一輪刻意沒有做的事

以下不是漏做，而是本輪刻意先不強推：

1. 沒有把所有 response shape 一次全面改成統一命名
2. 沒有把所有 API 的 `id` / `task_id` / `message_id` 強制改成單一 key
3. response contract 仍未全面統一
4. 沒有直接導入 Swagger / OpenAPI 產生流程

原因是 10.2 的定位還是先把後端 request contract 與來源責任收斂好，避免在基礎還沒穩時就往下疊。

## 9. 目前仍可注意的地方

這一輪做完後，還有幾個你後續檢查時可以特別注意的點：

1. `backend/contracts/` 已完成正式搬遷，但仍需避免把純 route 專屬 schema 全部塞進共用契約層
2. `blueprints/validation.py` 目前可接受，但本質上更像 HTTP validation infrastructure
   - 專案再變大時，可以再考慮移到更中性的 backend 共用位置
3. response contract 目前只做了第一階段盤點
   - request 已開始收斂，但 response 仍不是完全統一
