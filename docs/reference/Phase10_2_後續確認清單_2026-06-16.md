## 1. 哪些 contract 真的應該共用？

### 為什麼要確認

這一輪我們把不少 request schema 從 blueprint 抽到了 contract 層，但不代表每一個 schema 都天然適合做共用契約。

如果沒有再確認，後面很容易變成：

- 只是 route 專屬的 payload，也被塞進共用 contract 層
- `contracts/` 變成「所有 schema 的集中垃圾桶」
- 看起來收斂了，實際上只是搬家

### 目前狀態

目前已集中到：

- `task_contracts.py`
- `timeline_contracts.py`
- `knowledge_contracts.py`
- `auth_contracts.py`
- `profile_contracts.py`
- `todo_contracts.py`
- `group_contracts.py`

### 接下來要討論的問題

1. 哪些 schema 是 blueprint / service / tool 都可能共用的？
2. 哪些 schema 其實只服務單一路由？
3. 哪些 schema 其實應維持 route-owned，而不是硬抽成 backend-wide contract？

### 先用的判斷原則

- 若同一組欄位規則會跨 blueprint / service / tool 重複使用，就偏向共用
- 若它只對單一路由有意義，就不要為了「看起來整齊」硬抽

## 2. `validation.py` 目前放在 `blueprints/` 是否接受？

### 為什麼要確認

昨天我們已經講過，`validation.py` 現在不是主要問題，但它的語意其實比較像 backend 共用的 HTTP validation infrastructure，而不是 blueprint 私有邏輯。

### 目前狀態

目前 `backend/blueprints/validation.py` 主要負責：

- `validate_payload_or_400`
- `error_response`
- `error_from_exception`

它已經是跨 blueprint 共用，而不是只服務單一模組。

### 接下來要討論的問題

1. 以目前專案大小，先留在 `blueprints/` 可不可以接受？
2. 這個位置是暫時合理，還是我們認為它就是長期正解？
3. 若未來要搬，較合理的新位置會是哪種語意？

### 目前建議立場

- 短期：可以接受先留在 `blueprints/`
- 長期：不把它視為理論上最終位置

### 目前結論

1. 10.2 這一輪先不搬 `validation.py`
2. 原因不是它的位置最理想，而是目前搬遷收益不高，主要只是目錄語意優化，尚未形成實際維護痛點
3. 後續若開始整理 backend 共用 HTTP 基礎設施，再回頭評估是否搬到更中性的目錄，例如 `backend/http/`、`backend/api/` 或 `backend/common/`

而這次調整已正式把這層視為 backend 共用契約真相來源。

### 接下來要討論的問題

3. 是否避免把純 route 專屬 schema 因為方便而全部塞進 `backend/contracts/`？

### 目前建議立場

- `backend/contracts/` 已正式定案

### 為什麼要確認

但實際上不是這樣。

### 目前建議立場

## 5. protected fields 與 route-owned identifiers 的界線是否真的內化？

### 為什麼要確認

這點不是只有文件定義而已，它應該變成後續看 schema / route / payload 時的判斷習慣。

### 目前狀態

規劃文件裡已切出兩類：

1. server-owned / protected fields
2. route-owned identifiers

目前典型例子：

- protected fields：`user_id`、`actor_user_id`、`created_by`
- route-owned identifiers：`task_id`、`timeline_id`、`group_id`、`comment_id`

### 接下來要討論的問題

1. 之後看到 request body 自送 `user_id` 這類欄位時，我們是否會立刻覺得有問題？
2. 之後看到 body 與 path 同時承諾 `task_id` / `timeline_id` 時，我們是否會立刻警覺？
3. 這個界線是否已經足夠支撐後續 contract review？

### 目前建議立場

- 這是 10.2 的核心收穫之一
- 後面每次看 payload，都應該用這個分類再過一遍

### 補充理解

可以先用一句比較直白的方式記：

不是所有欄位都應該靠外層 payload 傳進來。

有些欄位應該：

1. 由 auth context 直接決定
   - 例如 `user_id`、`actor_user_id`
2. 由 route / path 決定
   - 例如 `task_id`、`timeline_id`
3. 由後端查詢或流程推導後確認
   - 例如 `created_by`
   - 某資源是否真的屬於某個 timeline / project
   - 某使用者是否真的具有 member / owner 身分

所以不能只想成「schema 驗證欄位格式就好」。

更完整的判斷是：

1. 這個欄位是不是 client 可以自由提供的資料？
2. 這個欄位是不是其實應由 server context 決定？
3. 這個欄位是不是其實應由 route 提供主來源？
4. 這個欄位是不是就算格式合法，也還要查 DB / 看權限 / 看流程狀態才知道能不能成立？

一句話版：

- 格式驗證可以靠 schema
- 欄位擁有權與業務合法性，很多時候要靠 context、route 或 service 查詢來決定

## 6. 建議討論順序

如果接下來要一個一個聊，建議順序如下：

1. 哪些 contract 真的應該共用
2. `services/contracts` 是否只是過渡站
3. `validation.py` 放 `blueprints/` 是否先接受
4. response contract 是否明確留到後續
5. protected fields / route-owned identifiers 是否已變成判斷習慣

原因是前兩個比較偏結構語意，先講清楚，後面幾個會比較好判斷。
