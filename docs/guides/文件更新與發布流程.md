# 文件更新與發布流程

> 適用情境：本次工程量大、跨前後端且含結構重構時。

## 目的

- 確保「程式實際狀態」與「文件紀錄」一致。
- 降低團隊交接成本，避免文件散落在根目錄與 `docs/` 多處。
- 建立可重複執行的發布節奏（更新文件 → 分批 commit → push）。

## 標準流程

### 1. 確認本次程式更動範圍

- 先確認本次涉及的模組：前端、後端、型別、契約、驗證腳本。
- 若更動量大，先規劃 commit 分批邊界（例如：程式碼 / 文件）。

### 2. 閱讀並更新 docs 內主文件

- 先更新 `docs/重構計畫.md`
- 再更新 `docs/進度追蹤.md`

更新原則：
- 先改「最後更新日期」
- 再改「狀態標記（完成/進行中）」
- 最後補上本次新增能力（例如 payload guardrails、契約文件、驗證結果）

### 3. 更新 README

至少補齊以下資訊：
- 本次新增開發流程或規範入口
- 新增驗證腳本命令（例如 `npm run guardrails:payload`）
- 相關文件索引（例如 `docs/reference/payload-contracts.md`）

### 4. 驗證

建議最少執行：
- 前端建置：`npm run build`
- 契約守門：`npm run guardrails:payload`

### 5. 分批 commit

建議批次：
- 批次 A：前後端程式重構、型別、mapper、guardrails 腳本
- 批次 B：docs 與 README 同步

commit 訊息建議格式：
- `feat(frontend): ...`
- `refactor(api): ...`
- `docs: ...`

### 6. push

- 確認分批 commit 都已完成。
- 推送到目前工作分支。
- 若有 PR 流程，同步附上本次文件更新重點與驗證結果。

## 本流程的完成定義

- `docs/` 內正式文件已更新完成。
- README 可直接引導新成員找到本次新增規範。
- commit 歷史可看出「程式更動」與「文件更動」的關聯。
