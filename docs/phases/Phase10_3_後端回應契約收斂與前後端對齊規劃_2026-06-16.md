# Phase 10.3：後端回應契約收斂與前後端對齊規劃

> 日期：2026-06-16  
> 主旨：在 Phase 10.2 已完成 request contract 與後端契約來源收斂後，進一步收斂 backend response contract，並以此作為前端 type / service 對齊的真相來源。  
> 定位：10.3 不是只修前端型別；它的順序是先收 backend response contract，再修 frontend consumer，最後產出第一版可檢查的 OpenAPI 文件。  
> 前提：`backend/contracts/` 已正式定為 backend 共用契約層，`validation.py` 暫時保留在 `blueprints/`，response contract 第二輪收斂明確留給 10.3 接續。

---

## 1. 為什麼 10.3 要先做 response contract

10.2 主要收掉的是：

1. request schema 來源
2. contract 目錄責任
3. protected fields / route-owned identifiers 邊界
4. blueprint / service / tool 共用契約層位置

但目前真正還比較鬆的，是 response 這一側。

現在 repo 內常見的 response 來源仍然混有：

1. blueprint 直接 `jsonify({...})`
2. service 回傳 payload dict，再由 blueprint 包成 response
3. agent/tool 自己走 envelope

如果這層不先收，後面很容易變成：

- 前端先修 type，但後端回應形狀還沒穩
- 同一個模組 create / update / list / AI response 各講各的
- request contract 已經有集中真相來源，response 卻仍然只靠印象維護

所以 10.3 的起手式不應是「先去修 frontend type」，而應是：

**先收 backend response contract，再讓 frontend 跟它對齊。**

---

## 2. 10.3 要回答的核心問題

10.3 應至少回答這幾件事：

1. 每個主要模組的 response 真相來源在哪？
2. 哪些 response 目前是 blueprint 直接承諾？
3. 哪些 response 已經接近 service / tool 穩定契約？
4. 哪些欄位名稱與 envelope 已經夠穩，可以保留？
5. 哪些 response shape 已經影響到 frontend type / service，必須在本輪一併收斂？

---

## 3. 本階段範圍

這一輪範圍不再採「高風險優先、其餘後補」的策略，而是直接以主要模組為收斂範圍：

1. `tasks`
2. `timelines`
3. `knowledge`
4. `copilot / agent`
5. `auth / profile`
6. `groups / messages / notifications`
7. `todos / trash`

原因：

1. 後面不管早做晚做，response contract 統一都還是得做
2. 若這輪只收一部分，剩下模組後面只會多更多 consumer，改動成本更高
3. request contract 與 `backend/contracts/` 已經定版，現在是一次把 response 一起收齊的合理時間點

---

## 4. 10.3 的收斂順序

### 4.1 先盤點 backend response 真相來源

對每個主要模組，至少先標出：

1. create / update / delete 等 mutation response
2. list / detail / summary 等 listing response
3. analysis / AI / report 類 response
4. tool / agent envelope

並且判斷目前由誰承諾：

1. blueprint
2. service payload
3. tool envelope
4. 其他 helper

### 4.2 這一輪直接完成全系統主要模組 response contract 統一

這一輪不再只停在「先定原則」，而是直接把全系統主要模組的 response contract 收成穩定版本。

範圍以本 phase 主要模組為主：

1. `tasks`
2. `timelines`
3. `knowledge`
4. `copilot / agent`
5. `auth / profile`
6. `groups / messages / notifications`
7. `todos / trash`

在這個範圍內，該統一的 mutation / listing / analysis / tool envelope，這一輪就直接統一，不再往後延。

統一時至少要明確處理：

1. mutation response
   - `message`
   - 主要 payload key
   - 是否回傳更新後資料
   - 相近操作是否維持同一套命名與 envelope
2. listing response
   - 是否接受裸陣列
   - 若需要 envelope，list / meta / paging 欄位如何固定
3. analysis / AI response
   - 可以保留專用外型，但欄位語意必須固定
   - 不同路徑不再各自長出相近但不同的 shape
4. tool response
   - 維持 `tool_envelopes.py` 的 success / failure 一致性

這一段的目標就是把主要模組的 response contract 這輪直接收掉，避免後續 consumer 越來越多後再回頭改得更痛。

### 4.3 再做 frontend type / service 對齊

當 backend response 真相來源比較清楚後，再對照：

1. `frontend/src/types/`
2. `frontend/src/services/`
3. 必要時的 store / component consumer

重點不是一次重寫所有前端，而是先抓：

1. 欄位名稱不一致
2. optional / required 假設不一致
3. frontend 以為存在、但 backend 其實不保證的欄位
4. 仍靠 cast 或模糊 envelope 消費的地方

### 4.4 最後補 focused 驗證

每條主要模組主線至少補其中一種：

1. backend response shape 測試
2. frontend service / type 對照測試
3. 契約差異表

### 4.5 再產出第一版 OpenAPI 文件

當主要模組的 request / response contract 已完成第一輪統一後，再產出第一版 OpenAPI 文件。

這裡的定位要先定清楚：

1. OpenAPI 是輸出層
2. 真相來源仍是 `backend/contracts/`、route 實作、response contract 與 focused tests
3. OpenAPI 用來幫助閱讀、檢查、對齊與後續工具化
4. 不用手寫一份和程式脫鉤的第二真相

OpenAPI 這輪至少要能幫忙回答：

1. 主要 endpoint 的 request schema 是否可讀
2. 主要 endpoint 的 response schema 是否可讀
3. response envelope 是否和實作一致
4. 前端 service / type 是否能依文件快速對照

若某些 endpoint 暫時無法乾淨輸出，也要在本輪記錄原因，而不是讓文件默默缺口。

## 5. 這一輪建議的實作策略

### 5.1 tasks

先看：

1. create / update / delete / toggle
2. members
3. comments / subtasks

先回答：

1. 哪些 response shape 已經穩定？
2. 哪些只是 blueprint 臨時 `jsonify(...)`？
3. 哪些前端已經依賴但名字仍不夠一致？

### 5.2 timelines

先看：

1. create / update
2. member / share / search user
3. weekly report / risk analysis / batch create tasks / AI generate

這塊要特別注意：

1. 一般 CRUD response
2. 分析類 response
3. AI 類 response

不要混成同一種收斂策略。

### 5.3 knowledge

先看：

1. upload / list / delete / reindex / preview
2. project files 相關路徑

重點是：

1. list / detail / action response 是否一致
2. frontend 是否依賴了未明講的欄位

### 5.4 copilot / agent

先看：

1. plan / reject / execute / replan
2. tool result envelope
3. trace / request_id / plan_id 相關欄位

這塊不適合硬套一般 CRUD response；應保留 agent 專用 envelope，但欄位語意要固定。

---

## 6. 本階段不做什麼

1. 不把既有 response shape 改成破壞前端的全新 envelope
2. 不在沒有 consumer 對照前，盲目大改既有欄位名稱
3. 不先從 frontend 反推後端
4. 不把 request contract 與 response contract 又混成同一個大整理
5. 不讓 OpenAPI 取代 `backend/contracts/` 成為新的手寫真相來源
6. 不把檔案下載、preview blob、Socket event 等非一般 JSON response 硬塞進同一種 JSON contract

---

## 7. 交付項目

10.3 這一輪建議至少交付：

1. 一份主要模組 response 真相來源盤點
2. 全系統主要模組 response contract 統一結果
3. 一份「已對齊 / 待對齊」清單
4. frontend type / service 對齊
5. focused tests 或契約差異表
6. 第一版 OpenAPI 文件或可生成 OpenAPI 的輸出入口

---

## 8. 完成標準

10.3 完成時，至少應該能回答：

1. 主要模組的 response 真相來源在哪？
2. 哪些 response 目前是 blueprint 直接承諾？
3. 哪些主要模組 response 已完成統一，不再只是較穩定的臨時慣例？
4. 哪些 frontend type / service 已完成對齊？
5. 第一版 OpenAPI 文件是否能反映主要 request / response contract？
6. 哪些模組若仍有特例，原因是否已被明確記錄？

### 至少要達到的狀態

1. backend response contract 不再只是口頭維護
2. 主要模組的 response shape 已進入可重複維護的統一版本
3. frontend consumer 不再優先靠猜測對接
4. request 已收斂、response 卻仍完全鬆散的狀態不再留在主要模組上
5. OpenAPI 已能作為閱讀與檢查入口，但不取代程式內契約真相來源

---

## 9. 10.3 與 OpenAPI 的銜接策略

10.3 可以開始產出 OpenAPI，但它的角色是「從已收斂契約輸出的閱讀與檢查層」。

建議策略：

1. 先完成主要模組 response contract 統一
2. 再把 request / response schema 掛到可輸出的 OpenAPI 入口
3. 產出第一版文件後，用它反查 frontend type / service 是否還有漂移
4. 若文件與實作不一致，以 `backend/contracts/` 與測試為準回頭修輸出，不讓文件獨立漂移

這樣做的好處是：

1. 後續閱讀 API 不用再只靠翻 blueprint
2. 前端對齊時有穩定參考
3. Codex 後續協助檢查契約時，也能更快定位欄位差異
4. 10.4 可以直接接閱讀版契約索引與維護原則，而不是重新盤點一次

---

## 10. 和後續 10.4 的關係

10.3 做完後，10.4 才比較適合補：

1. 閱讀版契約索引
2. 文件維護原則
3. OpenAPI 文件維護流程與輸出層接點

因為沒有先收 backend response contract，閱讀版文件就很容易又變成第二份不穩定真相。

---

## 11. 一句話版

10.2 收掉的是「後端 request 與 contract source」，  
10.3 要收掉的是「後端 response、前端 consumer 對齊，並產出第一版 OpenAPI 入口」。  

順序一定要是：

**先收 backend response contract，再修 frontend type / service，最後輸出 OpenAPI。**
