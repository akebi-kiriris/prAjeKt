# Phase 10.5：模組別主線導覽規劃

> 日期：2026-06-18  
> 主旨：在 Phase 10.1 ~ 10.4 已完成契約盤點、後端 contract 收斂、response / OpenAPI / frontend consumer 對齊與文件維護流程後，補一層「人能讀懂的模組主線導覽」。  
> 定位：10.5 不是再做一輪 contract refactor，也不是 10.6 的差異表；它要把每個主要模組從「頁面入口 → frontend type / service → API → backend route / contract / service → tests」串成可閱讀的路線圖。  
> 目的：讓未來回頭看 `tasks`、`timelines`、`knowledge`、`groups`、`copilot / agent` 時，不用重新翻整個 repo，也不需要一次理解所有細節。

---

## 1. 為什麼需要 10.5

10.1 ~ 10.4 已經回答了很多「契約在哪裡」的問題：

1. 哪些 API / 模組有 request / response schema
2. 哪些 contract 已集中到 `backend/contracts/`
3. 哪些 response 已接上 Pydantic model
4. 哪些 frontend consumer 已對齊
5. OpenAPI 如何匯出與維護
6. dynamic / binary / legacy-flexible 區塊如何標記

但這些文件偏向「契約與維護狀態」。它們可以告訴我某個 API 是否穩定，卻不一定能快速回答：

1. 我要看 `tasks` 主線時，應該先看哪個頁面？
2. frontend type、service、store、component 之間怎麼串？
3. backend route 進來後，會進哪個 service？
4. request / response contract 在哪裡？
5. 對應測試大概在哪些檔案？
6. 哪些地方只是閱讀入口，哪些地方才是真正實作？

所以 10.5 要補的是「閱讀路線」，不是再補一份 API 規格書。

---

## 2. 10.5 要回答的核心問題

每個模組導覽至少要能回答：

1. 使用者從哪個頁面或元件進入這條主線？
2. frontend 主要 type 在哪裡？
3. frontend service API wrapper 在哪裡？
4. 主要 store / component consumer 在哪裡？
5. 對應 backend route 在哪裡？
6. request / response contract 在哪裡？
7. backend service 或 domain flow 在哪裡？
8. 主要測試檔在哪裡？
9. 哪些區塊只需要知道入口，不需要現在深入？
10. 哪些區塊留給 10.6 的鬆動點清理，不在 10.5 改？

---

## 3. 這一輪的交付形式

建議先產出一份 reference 文件：

`docs/reference/Phase10_5_模組別主線導覽整理_2026-06-18.md`

這份文件應以「模組」為章節，而不是以 endpoint 為章節。

每個模組使用固定格式：

1. 這條主線在做什麼
2. 閱讀順序
3. frontend 入口
4. frontend type / service / store / component
5. backend route / contract / service
6. OpenAPI / contract 狀態入口
7. 測試入口
8. 不必在本輪深入的地方
9. 若未來要修，應該從哪裡下手

這份文件要寫給「未來的自己」看，所以可以保留一點白話說明，不需要像程式規格一樣過度壓縮。

---

## 4. 本階段範圍

10.5 先覆蓋以下主線：

1. `tasks`
2. `timelines`
3. `knowledge`
4. `groups / messages / notifications`
5. `copilot / agent`
6. 目前最不穩或最容易迷路的區塊總表

可以視需要補很短的 `auth / profile`、`todos / trash` 導覽，但它們不是 10.5 的主角。

原因：

1. `tasks` 與 `timelines` 是最常被其他功能依賴的業務主線
2. `knowledge` 是 RAG / AI suggest plan 的資料來源
3. `groups / messages / notifications` 有 REST、socket、snapshot、notification 多條事件流
4. `copilot / agent` 同時牽涉 frontend dock、agent API、tool planning、tool execution、trace / dynamic payload
5. 這些模組最容易讓人「知道有功能，但不知道從哪裡看起」

---

## 5. 本階段不做什麼

10.5 不做：

1. 不重構 backend route / service
2. 不新增 request / response contract
3. 不修 frontend type drift
4. 不逐條建立 endpoint 差異表
5. 不把 OpenAPI 改成更自動化的工具
6. 不把 `copilot / agent` dynamic payload 硬 schema 化
7. 不把文件寫成第二份完整 API 規格書
8. 不為了導覽而補大量重複說明

如果導覽過程中發現真正的契約不一致，只先記在「可能留給 10.6 的項目」，不要在 10.5 直接修。

---

1. ...

## 7. 各模組預期導覽重點

### 7.1 tasks

導覽重點：

1. 任務列表、任務建立 / 更新 / 刪除
2. task members
3. comments
4. files / upload / download
5. subtasks
6. upcoming tasks

這條主線要幫人理解：

1. `TasksView` / timeline detail 裡的 task 操作怎麼進 service
2. frontend `task` type 與 backend `task_contracts.py` 的關係
3. 哪些 response 是固定 mutation response
4. 哪些 list 維持 legacy-flexible shape
5. 測試應該先看哪些檔案

### 7.2 timelines

導覽重點：

1. timeline CRUD
2. timeline tasks
3. members
4. weekly report
5. risk analysis / notify
6. conflict check
7. AI generate tasks
8. AI suggest plan

這條主線要幫人理解：

1. `TimelineDetailDialog` 拆分後每個面板大概負責什麼
2. `timelineService` 如何對應 backend route
3. `timeline_contracts.py` 為什麼變成大型 contract 檔
4. RAG planning service 與 timeline plan suggestion response 的關係
5. 哪些 AI payload 已穩定，哪些只是保持現有 shape

### 7.3 knowledge

導覽重點：

1. 個人知識庫頁面
2. project files 區塊
3. upload / list / delete / reindex
4. download / preview
5. document events
6. RAG plan 如何使用 knowledge source

這條主線要幫人理解：

1. knowledge 不是只有一個頁面，而是同時服務使用者管理與 RAG
2. JSON response 與 binary response 要分開看
3. `knowledge_contracts.py` 與 `knowledge_service.py` 各自負責什麼
4. project-scoped permission 和文件事件流大概在哪裡

### 7.4 groups / messages / notifications

導覽重點：

1. group create / join / leave
2. group members
3. group messages
4. REST message payload 與 socket message payload
5. AI snapshot
6. unread counters
7. notifications

這條主線要幫人理解：

1. groups、messages、notifications 其實是同一組協作事件流
2. 哪些東西走 REST，哪些還牽涉 socket serializer
3. snapshot queued / latest / job status 是不同 response
4. notification list 與 counter / mutation response 的差別

### 7.5 copilot / agent

導覽重點：

1. CopilotDock
2. agent tools list
3. plan / execute / reject / replan
4. MCP execute
5. tool planner prompt
6. tool registry / tool envelopes
7. trace / metadata / dynamic payload

這條主線要幫人理解：

1. copilot frontend 不是直接呼叫工具，而是走 agent API
2. plan 與 execute 是兩段式流程
3. tool-specific result 保留 dynamic 是刻意設計，不是漏做
4. `backend/contracts/tool_inputs.py`、`tool_outputs.py`、`tool_envelopes.py` 各自的角色
5. 這條主線最適合在 10.6 或後續做更細的 dynamic payload 收斂

### 7.6 目前最容易迷路的區塊

這份總表不應該變成 bug list，而是幫閱讀者知道哪些地方要放慢：

1. `TimelineDetailDialog` 與其拆分子元件
2. timeline AI generate / suggest plan / RAG planning 的關係
3. group snapshot 的同步 / 非同步 response
4. message REST / socket serializer 共用邊界
5. copilot plan / execute / tool envelope / trace metadata
6. knowledge binary response 與 JSON contract 的分界

## 8. 和 10.4 / 10.6 的分工

### 10.4 已完成的是

1. 契約狀態矩陣
2. 文件維護原則
3. OpenAPI 維護流程
4. OpenAPI 覆蓋 / 缺口清單

10.5 不重做這些內容，只引用 10.4 的結論。

### 10.5 要完成的是

1. 模組閱讀路線
2. frontend / backend 檔案入口對照
3. 每條主線的責任邊界
4. 哪些地方不用現在深挖
5. 哪些問題可能留給 10.6

### 10.6 才適合做的是

1. 契約差異表
2. 高風險鬆動點清理
3. route response shape 與 frontend service type 的逐條比對
4. dynamic payload 進一步 schema 化
5. 實際修正程式碼

## 9. 完成標準

10.5 完成時，至少要能回答：

1. 我要看 `tasks` 主線，應該從哪些檔案開始？
2. 我要看 `timelines` AI / report / risk 相關主線，哪些檔案是入口？
3. `knowledge` 和 RAG planning 的關係要怎麼讀？
4. `groups / messages / notifications` 的事件流怎麼拆開看？
5. `copilot / agent` 的 plan / execute / tool contract 怎麼串？
6. 哪些地方只是目前最容易迷路，不代表現在要修？
7. 後續若要做 10.6，哪些主線最值得優先檢查？

### 至少要達到的狀態

1. 新人或未來的自己可以照文件找到主要模組入口
2. 每個模組都有 frontend / backend / tests 的最小路線圖
3. 文件不重複 10.4 的契約狀態矩陣
4. 文件不偷渡 10.6 的修正工作
5. 導覽文字足夠白話，能幫助重新建立心智模型

---

## 10. 一句話版

10.4 告訴我「契約現在穩不穩、文件怎麼維護」。  
10.5 要告訴我「我要讀某個模組時，從哪裡開始、一路看到哪裡、哪些地方先不要鑽太深」。  

這一輪的重點不是修，而是把專案主線畫成能走的路。
