# Phase 9.5：Agent 契約與邊界大修計畫

日期：2026-06-09  
階段定位：Phase 9.5 收斂後的大修波段，位於 **Phase 9.6 可觀測性 / benchmark 之前**  
目標：先把 Agent 主線的契約、輸入邊界、副作用工具語意與 service 權限邊界補到穩，再往 9.6 與後續擴工具走。

---

## 一、這次大修的定位

這次不是再往前加新能力，而是刻意停下來，把目前已經能跑的 Agent 主線做一次工程化收斂。

核心判斷是：

1. `plan -> confirm -> execute` 主流程已成立
2. Tool Registry、LangGraph Agent、CopilotDock 也已經有可用閉環
3. 但目前仍有一些「可以跑、但還不夠硬」的邊界
4. 如果現在直接跳去 Phase 9.6，可觀測性會建立在一個仍有鬆動契約的基礎上

所以這一波的目標不是擴功能，而是先把以下幾件事做紮實：

1. Tool input 內層契約硬化
2. nested payload / protected key 邊界補強
3. retry 與高副作用工具的安全邏輯收斂
4. service 內權限邊界重新拉直
5. 寫入型工具的 user-visible 語意修正

---

## 二、為什麼要先做這波

目前已確認的狀況是：

### 1. Tool 外層 schema 已存在，但內層仍偏鬆

例如：

1. `CreateTaskToolInput.data`
2. `UpdateTaskToolInput.data`
3. `CreateTimelineToolInput.data`
4. `TimelineBatchCreateTasksToolInput.tasks`
5. `TimelineConflictCheckToolInput.payload`

這些欄位在施工前多數仍是 `dict[str, Any]` 或 `list[dict[str, Any]]`。  
目前已完成第一波收斂，已改為明確 payload model / item model，並補上 `extra="forbid"` 與對應 contract 驗證。

### 2. Agent sanitize 目前主要只擋第一層

施工前 protected keys 主要只會從最外層 payload 移除，但像：

1. `data.user_id`
2. `payload.created_by`
3. `tasks[].timeline_id`

這類 nested 欄位當時還沒有統一清理策略。  
目前已改成遞迴清理，`agent_nodes.py` 與 `copilot_service.py` 兩邊都已對齊。

### 3. retry 路徑目前未依副作用等級做差異化

施工前錯誤是否 retry 主要依 `retryable` 決定，方向沒有錯；  
目前已先完成第一版保護：高副作用工具若遇到 retryable error，不再直接自動重試，而是改走 `ask_user`。  
完整 idempotency key 設計仍保留為後續 follow-up。

### 4. 部分寫入型 service 的權限仍偏 blueprint 依賴

Agent / Tool Registry 直接走 service 時，service 本身的 actor 驗證就不能只靠外層 route guard。  
目前已補到 `task_service.py`、`timeline_service.py`、`knowledge_service.py`。

### 5. 部分工具名稱或文案，和實際副作用語意不完全一致

尤其像 `batch_create_tasks_for_timeline`，實際上不只是 append tasks，還可能：

1. 保留部分舊任務
2. 軟刪未保留舊任務
3. 新建任務
4. 重建依賴

這會影響 plan preview 與使用者確認時的心理模型。  
目前已先修正 `user_visible_label`、Agent 成功訊息與 CopilotDock 摘要文案，internal tool name 暫時維持不變。

## 四、工作主題分組

## A. Tool Input 內層契約硬化

### 目標

把目前外層已有、但內層仍鬆散的 tool input 改成真正可驗證的結構。

### 優先目標

1. `backend/services/contracts/tool_inputs.py`
2. `backend/services/contracts/task_contracts.py`
3. `backend/services/contracts/timeline_contracts.py`

### 第一批建議收斂的模型

1. `CreateTaskToolInput.data`
   - 目標：改為明確的 `CreateTaskToolPayload`
2. `UpdateTaskToolInput.data`
   - 目標：改為明確的 `UpdateTaskToolPayload`
3. `CreateTimelineToolInput.data`
   - 目標：改為明確的 `CreateTimelineToolPayload`
4. `TimelineBatchCreateTasksToolInput.tasks`
   - 目標：改為 `list[BatchCreateTaskItem]`
5. `TimelineConflictCheckToolInput.payload`
   - 目標：直接對齊既有 `ConflictCheckInput` 或以 wrapper 明確承接

### 原則

1. 能重用既有 `TaskCreateInput` / `TaskUpdateInput` / `ConflictCheckInput` 就不要重造
2. 需要 Agent tool 專用欄位時，才在外層再包一層
3. 所有內層 schema 預設 `extra="forbid"`
4. 預設值與 service 既有行為要保持一致，避免偷偷改 contract

---

## B. Protected Keys 與 Nested Payload 邊界補強

### 目標

避免外部 payload 在 nested 結構中夾帶敏感 scope 欄位。

### 主要檔案

1. `backend/chains/agent_nodes.py`
2. `backend/services/copilot_service.py`

### 要做的事

1. 將 `_sanitize_user_payload()` 從只處理第一層，提升為可遞迴處理 dict / list
2. 定義這次要統一清掉的 protected keys：
   - `user_id`
   - `actor_user_id`
   - `created_by`
   - `timeline_id`
   - `task_id`
   - `group_id`
3. 明確區分：
   - 由系統 context 注入的欄位
   - 可由模型 / 前端提供的業務欄位

### 驗收重點

1. 第一層覆寫要被清掉
2. nested dict 覆寫要被清掉
3. list item 內夾帶敏感欄位也要被清掉
4. 合法欄位不能被誤刪

---

## C. Retry 與高副作用工具保護

### 目標

讓 retry 邏輯不只看 `retryable`，也開始考慮工具副作用等級。

### 主要檔案

1. `backend/chains/agent_nodes.py`
2. `backend/services/tools/registry.py`
3. `backend/services/tools/error_mapper.py`

### 這波至少要完成的底線

1. 盤點目前 high side-effect tools：
   - `create_task_for_user`
   - `update_task_for_member`
   - `create_timeline_for_user`
   - `batch_create_tasks_for_timeline`
   - `generate_group_snapshot`
   - `upload_and_index_knowledge_document`
2. 明確區分：
   - 單純 validation error：不 retry
   - upstream timeout / unavailable：可 retry
   - 高副作用工具失敗：是否允許自動 retry，要有清楚規則

### 建議方向

第一版不一定要一次做完整 idempotency key，但至少要做到：

1. 高副作用工具不要無條件沿用一般 retry 心智模型
2. 必要時在 route 層改成 `ask_user` 或 `stop`
3. 對未來 idempotency key 預留欄位與文件位置

### 這波不強求的事

1. 不必一次把所有 write tool 都做完整 idempotency
2. 不必為了這波就重寫整個 route-by-error 策略

## D. Service 權限邊界重整

### 目標

把「寫入型 service 的權限檢查」從只靠 blueprint guard，提升為 service 本身也有 actor 邊界。

### 核心想法

Agent 化之後，service 不是只會被 HTTP route 呼叫。  
只要工具直接進 service，service 自己就要知道：

1. 誰在操作
2. 是否有權限
3. 這次操作的資源範圍是什麼

### 主要檔案

1. `backend/services/task_service.py`
2. `backend/services/timeline_service.py`
3. `backend/services/tools/handlers.py`
4. `backend/services/knowledge_service.py`

### 第一批優先

1. 再次盤點所有直接被 Tool Registry 走到的寫入 service
2. 統一 `operator_user_id` / `actor_user_id` 的命名與傳遞方式
3. 避免 handler 把 payload 內的 actor 欄位當真，而要由 context 注入

### 原則

1. HTTP guard 保留
2. service 內權限補強
3. 不為了「純工程美感」做過度抽象

## 六、測試策略

這波不是只改 code，要同步把「大修護欄」補完整。

### A. Tool / Agent 邊界測試

1. nested protected keys 會被清除
2. malformed nested payload 會正確走 validation error
3. contract forbid extra fields 生效
4. 舊有成功案例不退化

### B. Service / Handler 測試

1. 寫入型 service 權限不足時正確拒絕
2. handler 不信任 payload 內 actor 欄位
3. batch create item schema 不允許亂塞欄位
4. conflict payload 型別錯誤時正確回標準 error envelope

### C. Retry / Side-effect 測試

1. low-risk read tool 可依既有規則 retry
2. high-risk write tool 不會在不安全情況下默默重試
3. 錯誤 route 仍保持可預測

### D. 前端 / 文案對齊

1. CopilotDock 步驟摘要符合實際語意
2. 不會再把 replace-like 操作描述成單純 append

2. 這些不是全部都危險，但屬於 Agent 契約的延伸區

建議定位：

1. 本次大修主線之外的「第二層 Agent 周邊」
2. 若 Wave 2 / Wave 3 收完後再評估是否擴修

### 3. `backend/services/contracts/tool_outputs.py`

目前觀察：

1. 多數 output 仍是 `result: dict[str, Any]`
2. 這比較偏 output 硬化，不像 input boundary 那麼急

建議定位：

1. 不納入這次主線
2. 之後做 Phase 9.6 trace / benchmark 前，至少先把 Agent 會直接讀的幾個 output 收掉

## 十四、後續總體拆法

如果把整個 repo 的驗證收斂完整拆開，建議分三條線，不要一次混做：

### Track A：Agent 主線邊界大修

就是本文件目前的 Wave 1 ~ Wave 5。

### Track B：全域 Blueprint Validation 收斂

範圍：

1. `auth`
2. `groups`
3. `profile`
4. `knowledge`
5. `todos`
6. `tasks/timelines` 中仍停留在 blueprint 的殘餘鬆動點

目標：

1. 每個 mutation route 都有清楚 payload model
2. 非空、trim、型別、enum、query param 規則集中化
3. route 層不再散落重複驗證邏輯

### Track C：Service Contract / Output Schema 收斂

範圍：

1. service input contract
2. service output / response shape
3. Agent 會讀的 output schema

目標：

1. input 先硬
2. output 再硬
3. trace / benchmark 最後建立在穩定 shape 上

## 十五、這次到底算不算範圍很亂

不算。

你現在的狀況比較像是：

1. 已經做到一個會開始互相牽動的階段
2. 你有感覺到「只修 Agent 表面，好像底下還有別的鬆動點」
3. 但你也知道不能整個 repo 一次翻掉

這其實不是混亂，反而是有在抓真正的工程邊界。

真正會讓事情變混的是：

1. 明知道其他地方也鬆，卻假裝只有眼前那一個檔案有問題
2. 或反過來，一口氣把所有 validation 問題全包進同一波

所以這次的正確做法就是：

1. 先把 Agent 主線這包收乾淨
2. 把其他區域明確列成 backlog
3. 等這包完成，再進第二波全域驗證收斂

這樣後續我接手執行時，才會是「一波一波收」，不是「看到哪修到哪」。
