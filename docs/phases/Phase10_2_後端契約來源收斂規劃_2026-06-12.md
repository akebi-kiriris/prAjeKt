# Phase 10.2：後端契約來源收斂規劃

> 日期：2026-06-12  
> 目的：把 Learnlink 後端目前分散在 blueprint、validation helper、service contracts、tool contracts、guard 與 response builder 的「契約來源」整理清楚，並定義後續收斂方式。  
> 定位：10.2 不是直接全面改寫，而是先把「哪裡才算契約真相」定清楚，讓 10.3 的前後端對齊與之後的 OpenAPI 輸出有穩定地基。

---

## 1. 為什麼 10.2 要先做

10.1 已經證明了一件事：

目前系統不是沒有契約，而是契約來源有點分散。

同一條 API 主線，現在可能同時牽涉：

1. blueprint 內的 Pydantic payload
2. `blueprints/validation.py` 的共用驗證與錯誤輸出
3. service 層自己的 domain contract
4. guard decorator 的權限邊界
5. tool input / output / envelope contract
6. blueprint 直接 `jsonify(...)` 的 response shape

如果這一層不先收斂，後面就會很容易發生：

- 前端對齊的不是「真正來源」，而是某次剛好看到的 shape
- OpenAPI 只能輸出某一部分契約，卻代表不了整體行為
- 同一個 domain 同時有兩套 schema，但沒人知道誰才是主版本

所以 10.2 的責任不是「做更多文件」，而是先回答：

後端哪些地方才是契約來源？哪些只是消費者？哪些是行為邊界但不是 schema？

---

## 2. 目前後端契約來源現況

依照 repo 現況，可以先分成五類：

### 2.1 Blueprint Request Payload

目前大量存在於：

- `backend/blueprints/tasks.py`
- `backend/blueprints/timelines.py`
- `backend/blueprints/todos.py`
- `backend/blueprints/auth.py`
- `backend/blueprints/profile.py`
- `backend/blueprints/groups.py`
- `backend/blueprints/knowledge.py`

特性：

- 靠近 HTTP 入口
- 適合處理 route 專屬欄位驗證
- 目前很多 schema 還直接寫在 blueprint 裡

風險：

- 不同 blueprint 容易各寫各的
- 和 service contract 重疊時，可能出現雙軌驗證

### 2.2 Blueprint Validation / Error Helper

核心檔案：

- `backend/blueprints/validation.py`
- `backend/blueprints/guards.py`

特性：

- 已經是全域共用入口
- 控制 `VALIDATION_ERROR` / `BAD_REQUEST` / `FORBIDDEN` 等 HTTP 錯誤語義

定位：

- 它是「HTTP 契約基礎設施」
- 不是 domain schema 本身

### 2.3 Service Domain Contracts

核心檔案：

- `backend/services/contracts/task_contracts.py`
- `backend/services/contracts/timeline_contracts.py`
- `backend/services/contracts/README.md`

特性：

- 比較接近 domain/service 真正想承諾的輸入格式
- 已有部分正規化與跨欄位檢查

風險：

- 目前只覆蓋部分 domain
- 和 blueprint payload 還沒有明確主從關係

### 2.4 Tool Contracts

核心檔案：

- `backend/services/contracts/tool_inputs.py`
- `backend/services/contracts/tool_outputs.py`
- `backend/services/contracts/tool_envelopes.py`
- `backend/services/tools/registry.py`
- `backend/services/tools/handlers.py`

特性：

- 這塊其實已經最接近「正式契約層」
- `extra="forbid"`、output schema、envelope 都相對明確

定位：

- 這是 agent/tool 對外穩定介面的主要真相來源
- 不應再回退成隨意 dict

### 2.5 Response Shape / Serializer

目前主要來源分兩種：

1. blueprint 直接 `jsonify({...})`
2. service 回傳 payload dict，再由 blueprint `jsonify(payload)`

這是目前 10.2 最需要補強定義的地方，因為：

- request schema 已經有不少 Pydantic
- response 卻大多還是靠散落 dict 口頭維護

## 3. 10.2 的核心判斷原則

### 3.1 什麼算「欄位契約」

屬於欄位契約的東西：

1. 欄位名稱
2. 欄位型別
3. 必填 / 選填
4. 是否允許 `null`
5. enum 合法值
6. 單純資料正規化
7. 純跨欄位一致性檢查

這些應該盡量收斂到 schema / contract model。

### 3.2 什麼算「業務規則」

屬於業務規則的東西：

1. 目前使用者是否有權限
2. 某資源是否存在
3. 狀態是否允許這次操作
4. 是否要發通知
5. 是否要寫 DB / 觸發副作用
6. 是否允許跨專案、跨成員操作

這些應該留在 service / guard / domain flow，不應硬塞進 schema model。

### 3.3 什麼算「受保護欄位」

受保護欄位指的是：

- 前端或模型不應直接自送
- 必須由 route context / auth context / system 注入

目前已明確存在的例子：

- `user_id`
- `actor_user_id`
- `created_by`
- `timeline_id`
- `task_id`
- `group_id`

這些欄位後續應該統一列入 protected fields 索引，而不是分散在各處靠記憶。

## 4. 10.2 的收斂策略

這一階段不追求一次到位，而是採三層收斂。

### 4.1 第一層：定義主從關係

先明確每一種契約來源的角色：

1. HTTP request schema
   - blueprint payload 或抽出的 request schema
2. domain/service contract
   - service 真正依賴的資料契約
3. tool contract
   - agent/tool 對外穩定介面
4. response contract
   - mutation / analysis / listing 回傳結構
5. error envelope
   - 全域錯誤協議

### 4.2 第二層：優先收斂高風險模組

本輪優先順序：

1. `tasks`
2. `timelines`
3. `knowledge`
4. `copilot / agent`

原因：

- 10.1 已經確認它們是高風險區
- 這些模組剛好跨到 HTTP、service、tool、frontend 多層

### 4.3 第三層：建立 response contract 慣例

目前最鬆的是 response shape，所以 10.2 要先建立一個最低原則：

1. mutation response
   - 優先 `{ message, id? / count? / resource? }`
2. listing response
   - list payload 是否保留裸陣列，要有明確規範
3. analysis / AI response
   - 專用 envelope 可保留，但要有固定欄位說明
4. tool response
   - 維持 `tool_envelopes.py` 的 success/failure 一致性

## 5. 建議目錄策略

10.2 不一定要在這一輪把所有檔案搬完，但應先確立目標結構。

建議方向：

### 5.1 backend/blueprints

保留：

- route
- auth / guard
- HTTP 層錯誤映射
- request parsing

逐步減少：

- 大量 domain schema 直接內嵌在 blueprint

### 5.2 backend/services/contracts

逐步收斂成主要契約層：

- `request/` 或 domain contract models
- `response/` 或 domain response models
- `tool_inputs.py`
- `tool_outputs.py`
- `tool_envelopes.py`
- 共用 enum / shared field model

### 5.3 backend/services / domain layer

保留：

- 商業規則
- permission-sensitive decision
- DB / repository coordination
- side effects

不再承擔：

- 任意 shape 的半隱性 payload 協議

### 5.4 docs/reference

這一層不作為真相來源，但要有索引文件指回真正程式位置。

所以本輪建議新增：

- `docs/reference/backend_契約來源索引.md`

用途：

- 快速說明每個模組的 request / response / guard / tool 契約在哪
- 作為之後 OpenAPI 對接前的人工入口地圖

## 7. 和 Swagger / OpenAPI 的關係

10.2 做完後，才比較適合開始評估 `APIFlask` / `flask-smorest` / 其他 OpenAPI 生成方案。

原因是：

1. 到那時 request schema 來源會比較明確
2. response shape 不會那麼散
3. protected fields 與 guard 邊界也比較清楚

換句話說：

10.2 不是反對 Swagger，而是在替 Swagger 清地基。

## 8. 10.2 完成標準

完成 10.2 之後，至少要能回答：

1. 每個主要模組的 request schema 真相來源在哪？
2. 哪些地方只是 HTTP 入口驗證，哪些是 domain contract？
3. 哪些欄位是 protected fields？
4. response shape 現在主要由哪一層承諾？
5. 若要接 OpenAPI，應該從哪一層開始輸出？

只要這五題能回答，10.3 的前後端對齊就會比現在輕鬆很多。
