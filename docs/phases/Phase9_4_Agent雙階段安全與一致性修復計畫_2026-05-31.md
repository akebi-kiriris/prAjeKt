# Phase 9.4 補充：Agent 雙階段安全與一致性修復計畫

> 日期：2026-05-31  
> 目的：針對 9.4 首版實作的安全與流程缺陷，先對齊問題與修復方案，再進入正式修補。

---

## 一、背景與目標

9.4 首版已完成 `Plan -> Confirm -> Execute` 主流程，但在實測與審視後，發現多項「高風險安全邊界」與「流程一致性」問題。

本文件目標：

1. 將已確認缺陷條列化（含風險等級）
2. 定義每一項的修復策略與落地點
3. 明確驗收條件（Done Criteria）

---

## 二、缺陷清單（已確認）

### P0（Critical）Agent 可繞過權限邊界

現象：

1. `tool_payloads` 可帶入 `user_id` 等敏感欄位，且目前組裝 payload 為「外部優先」。
2. tool handler 直接調用 service，非經 blueprint guard，若 service 未做 actor 驗證，可能形成越權操作。

風險：

1. 可讀取他人任務/留言
2. 可對他人資源執行更新/批次操作
3. 造成資料安全與租戶隔離破壞

---

### P1（High）Plan 已確認後仍可替換實際參數

現象：

1. `create plan` 只保存工具順序，不保存核准參數快照。
2. `execute` 階段仍可傳新 `tool_payloads`，導致「預覽內容 ≠ 實際執行」。

風險：

1. 使用者確認失去意義
2. 不符合 approved snapshot 設計

---

### P1（High）Plan 可被重複執行（非冪等）

現象：

1. 狀態機對 `executing` 請求未嚴格拒絕
2. 重送或併發請求可能重複寫入

風險：

1. 重複建立專案/任務
2. 產生不可預期資料污染

---

### P1（High）雙階段確認非強制

現象：

1. `/agent/execute` 在無 `plan_id` 時仍允許直接執行
2. `confirm=bool(...)` 有字串真值陷阱（`"false"` 可能被當 True）

風險：

1. 繞過確認步驟
2. UX 與安全契約不一致

---

### P2（Medium）Copilot 上下文在多數頁面不足

現象：

1. 路由多為靜態，Dock 主要從 params/query 取 id
2. 常見操作缺少 `timeline_id/task_id/group_id`

風險：

1. 工具缺參數失敗率高
2. 使用者體感「Agent 常不懂我在看哪個物件」

---

### P2（Medium）不支援需求可能誤報完成

現象：

1. 未命中意圖時 fallback 到查詢工具
2. finalize 可能回「任務已完成」

風險：

1. 錯誤成功訊號（false positive）
2. 破壞信任與可觀測性

---

### P2（Medium）前端測試 selector 漂移

現象：

1. 測試仍依賴舊 selector（如 `title="編輯"`）
2. 元件改版後測試未同步

風險：

1. 測試綠燈失真
2. 回歸保護力下降

---

### P3（Low）格式衛生（EOF/BOM）

現象：

1. 多個 Vue 檔案出現 EOF 空白行
2. 部分檔案疑似含 BOM

風險：

1. PR diff 噪音升高
2. 跨平台編輯行為不一致

---

## 三、修復策略（對齊版）

### A. 權限邊界收斂（P0）

1. `tool_payloads` 改為「系統欄位不可覆蓋」
2. 建立保護欄位清單：`user_id / actor_user_id / created_by / timeline_id / task_id / group_id`
3. 由 context 與 server-side 推導值為準，忽略外部同名欄位
4. service/tool 層加入 actor 一致性檢查（必要時新增 wrapper）

驗收：

1. 用戶嘗試傳 `user_id=999` 不生效
2. 讀/寫他人資源一律被拒絕（4xx）

---

### B. Approved Snapshot 強化（P1）

1. `plan` 儲存：
   - 工具順序
   - 每一步核准參數快照（sanitized payload）
2. `execute` 僅讀取 plan snapshot，拒絕外部覆蓋
3. 回傳 `diff_from_plan`（若系統補值則需明示）

驗收：

1. execute 不接受 runtime payload 改寫
2. 預覽與執行內容可對帳

---

### C. Plan 冪等與狀態機鎖定（P1）

1. `planned` 才可進入 `executing`
2. `executing/succeeded/failed/rejected/expired` 一律拒絕再次執行
3. 同 `plan_id` 第二次 execute 回 `409 PLAN_ALREADY_EXECUTED`
4.（可選）加輕量鎖/nonce 防併發

驗收：

1. 重送 execute 不重複寫入
2. 並發 execute 只允許一次成功

---

### D. 強制雙階段流程（P1）

1. production 模式下 `/agent/execute` 必須有 `plan_id`
2. direct execute 改為內部 debug 開關（預設關閉）
3. `confirm` 型別嚴格為 boolean，字串一律 400

驗收：

1. 無 plan_id 執行請求直接拒絕
2. `"false"` 不可被視為 True

---

### E. 上下文補齊策略（P2）

1. 前端 context store：由目前選取物件同步更新（而非只靠 route）
2. 進入 task/timeline/group 詳情時，顯式寫入 active context
3. Dock 顯示「已鎖定上下文類型」與缺失提示

驗收：

1. 常見場景（任務詳情、群組、時間軸）可穩定帶到對應 id

---

### F. 不支援需求保守回覆（P2）

1. 新增 `unsupported_intent` 判斷（白名單語義）
2. 未支援時回 `ask_user`/`unsupported`，不可回完成
3. finalize 文案改為契約化（完成/部分完成/未支援）

驗收：

1. 輸入「寄 email」不會回成功

---

### G. 測試與格式衛生（P2/P3）

1. 更新前端測試 selector（改 role/name 或 `data-testid`）
2. 補 backend 安全回歸測試：
   - payload override 阻擋
   - plan snapshot 不可改寫
   - execute 冪等
3. 執行 EOF/BOM 清理與 `git diff --check` 歸零

驗收：

1. 測試綠燈
2. `git diff --check` 無格式警告

---

## 四、建議修補順序

1. Wave 1（P0 + P1）
   - 權限邊界
   - snapshot 鎖定
   - execute 冪等
   - 強制雙階段
2. Wave 2（P2）
   - context 補齊
   - unsupported intent
   - selector 修補
3. Wave 3（P3）
   - EOF/BOM 清理

---

## 五、9.4 Done（修補版）

1. 無法透過 payload 覆蓋 actor/context 身份欄位
2. Confirm 後執行內容與 plan snapshot 一致
3. 同 plan 不可重複執行
4. execute 必須走 plan-confirm 流程
5. 不支援需求不會誤報成功
6. 測試與格式檢查通過
