# Phase 10：全系統契約收斂與前後端對齊規劃

> 日期：2026-06-12  
> 主旨：把整個系統的後端 schema、前端 type、request/response、agent/tool payload 與閱讀版文件收斂成同一套契約語言，降低開發時前後端鬆散、欄位漂移與驗證散落的成本。  
> 定位：這一階段不是只處理 AI/agent，而是面向整個系統的前後端契約維護 phase；agent 只是其中一個高風險模組。  
> 完成定義：Phase 10 收尾時，整個系統主要模組的前後端契約應已對齊，高風險欄位與鬆散 response shape 已被收斂，後端真相來源與前端消費方式都能穩定維護。

---

## 1. Phase 10 要解決什麼問題

目前專案在開發時，偶爾會遇到這幾種典型狀況：

1. 前端 type 與後端實際 request/response 不完全一致
2. 某些欄位前端以為可以送，但其實應由後端決定
3. 驗證規則散落在 blueprint、helper、tool contract、service guard，不容易快速定位
4. 有閱讀版文件，但不一定能保證它和真正契約同步

而且這些問題並不限於 copilot/agent，也會出現在：

- tasks
- timelines
- knowledge
- groups / messages / notifications
- profile / auth
- copilot / agent

所以 Phase 10 的核心不是「補一套好看的 API 文件」，而是：

- 先讓契約來源收斂
- 再讓前後端對齊
- 最後才為後續 OpenAPI / Swagger / 機器可讀輸出留好接點

---

## 2. 本階段成果定義

完成 Phase 10 之後，至少要做到：

1. 知道整個系統中高風險 API / payload 的契約來源在哪裡
2. 知道哪些驗證屬於欄位契約，哪些屬於業務規則
3. 知道前端目前直接依賴哪些高風險欄位
4. 有一份「已對齊 / 待對齊」清單，不再只靠印象維護
5. 有可延伸到 OpenAPI / Swagger 的輸出接點，但不強迫此階段全量導入
6. 主要模組不再長期存在「前端型別一套、後端實際回傳另一套」的鬆動狀態
7. 高風險模組的契約差異已有收尾策略，不因原始分段編號限制而中止

### 3.6 全系統收尾與鬆動點清理

這一段的目的，是確保 Phase 10 的終點不是只有規劃與局部對齊，而是整體系統真正進入較穩定的契約狀態。

- [ ] 建立主要模組契約差異表
  - `tasks`
  - `timelines`
  - `groups`
  - `knowledge`
  - `copilot / agent`
- [ ] 逐步收掉高風險鬆動點
  - response shape 與 frontend service type 不一致
  - payload model 混用 entity model
  - protected fields 邊界不明

- [ ] 確認主要模組已達到可穩定維護狀態

  - 前端不再靠 cast / 猜測消費高風險資料

- [ ] 允許視實際收斂進度，持續往 `10.6.x`、`10.7+` 延伸
  - 分段是節奏工具，不是收尾上限

## 4. 建議執行順序與維護護欄

1. 每次處理一條契約主線時，先做契約比對
   - 先找 backend route / schema / response
   - 再找 frontend service / type / store / component
   - 最後記錄差異與修正方向
2. 每次修契約時，先修真相來源，再修消費端
   - 先收斂 backend schema / response contract / protected fields
   - 再修 frontend type / mapper / service
   - 最後補閱讀版文件或契約索引
3. 每次遇到欄位規則時，先判斷責任層
   - 欄位格式與 request/response shape 留在 schema contract
   - 權限、流程限制、商業判斷留在 service / domain guard
4. 每次處理高風險 API 時，至少同步檢查四個點
   - backend request schema
   - backend response shape
   - frontend type / payload
   - focused tests 或契約差異表
5. 每完成一批契約修正時，更新模組狀態
   - 哪些模組已對齊
   - 哪些模組仍有鬆動點
   - 是否需要延伸到 `10.6.x` / `10.7+`

---

## 5. 本階段不做什麼

1. 不追求一次把所有 endpoint 全量文件化
2. 不為了文件而先做大規模框架替換
3. 不把所有驗證硬塞進單一檔案
4. 不在理解仍模糊時直接展開大型架構重構
5. 不把焦點拉回 Notion clone 式功能擴張

---

## 6. 與後續 Phase 的關係

- `Phase 10`
  - 先收斂整個系統的契約來源與前後端對齊方式
- `Phase 11`
  - 在已較穩定的契約上補 Integration Test
- `Phase 12`
  - 在較穩定的 agent / AI 流程上做 Evaluation
- `Phase 13`
  - 在較穩定的執行路徑上補完整 Observability

所以 Phase 10 的價值是：

先把「整個系統到底承諾了什麼」說清楚，後面測試、評測、可觀測性才不會建在鬆動的地基上。
