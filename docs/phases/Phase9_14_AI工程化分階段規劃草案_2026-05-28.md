# Phase 9~14：AI 工程化分階段規劃草案（單人精簡版）

> 日期：2026-05-28  
> 目標：維持「先最小可跑，再逐步擴充」，避免過度工程化

---

## 規劃原則

1. 每個 Phase 都先交付一個可運行最小版本（MVP）。
2. 先保證可靠性與可維護性，再擴功能。
3. 單人開發優先「低心智負擔 + 可快速回復」。

---

## Phase 9：Tool Calling / Agent Runtime（MVP）

### 目標
- 建立可控、可驗證的 Tool Calling 主流程。

### 最小交付
1. Tool Registry（統一註冊入口）。
2. Tool Schema（Pydantic 輸入/輸出契約）。
3. Tool Permission（白名單或角色限制）。
4. Timeout / Retry（每個 tool 的最小容錯策略）。
5. Execution Log（至少記錄輸入摘要、耗時、結果狀態）。
6. Result Validation（tool 回傳再驗證一次）。

### 延後項（先不做）
1. 複雜的多層 Agent Planner。
2. 全量 LangGraph 複雜編排。

---

## Phase 10：AI Workflow Runtime / Queue（MVP）

### 目標
- 把 AI 工作從同步 request-response 抽離，提升穩定性。

### 最小交付
1. Async Job Queue（可入列/出列）。
2. Job Status：`pending / running / completed / failed`。
3. Retry（基礎重試次數與間隔）。
4. Execution History（保留每次執行紀錄）。
5. 查詢 API（可查單一 job 狀態）。

### 第二階段再補
1. `cancel`（取消流程）。
2. `retrying` 狀態細分。
3. WebSocket/SSE 即時進度。

---

## Phase 11：RAG / AI Eval Framework（先小後大）

### 目標
- 讓模型/檢索優化有客觀比較基準。

### 最小交付
1. 小型 Benchmark Dataset（先 20~50 題）。
2. Retrieval Eval（命中率、Top-k 命中觀察）。
3. Groundedness 基礎檢查。
4. Hallucination 基礎檢查。
5. Prompt A/B Compare（先固定 1~2 組）。

### 擴充項
1. Chunk Strategy Compare。
2. Provider Compare（如 OpenAI vs Gemini）。
3. Rerank on/off、Top-k=3 vs 5 等矩陣化實驗。

---

## Phase 12：AI Observability（核心四指標先行）

### 目標
- 先知道系統是否健康，再談進一步優化。

### 最小交付
1. Latency（端到端延遲）。
2. Failure Rate（失敗率）。
3. Token Usage（使用量）。
4. Cost Tracking（成本估算）。

### 第二階段再補
1. Tool Usage 分佈。
2. Retrieval Score 趨勢。
3. Retry Count 與重試原因分類。
4. Dashboard 視覺化。

---

## Phase 13：Plugin / Extension Architecture（平台化起點）

### 目標
- 讓功能以模組方式擴充，不污染核心流程。

### 最小交付
1. Dynamic Tool Registration（動態註冊）。
2. External Tool Loading（外部工具載入約定）。
3. Feature Module 邊界（核心 vs 擴充）。
4. Runtime Config（可開關模組）。

---

## Phase 14：Multi-agent / Planner（可選，最後做）

### 目標
- 在前面基礎穩定後，再引入多代理流程。

### 建議流程
1. Planner
2. Retriever
3. Tool Executor
4. Validator
5. Response Synthesizer

### 進入條件
1. Phase 9~12 已穩定至少一輪。
2. 有明確痛點需要多代理拆工。

---

## 建議執行順序（單人版）

1. Phase 9（工具契約與執行護欄）
2. Phase 10（非同步工作流）
3. Phase 11（最小評估框架）
4. Phase 12（最小可觀測性）
5. Phase 13（擴充架構）
6. Phase 14（多代理，可選）

---

## 驗收原則（每個 Phase 共用）

1. 有最小可跑流程（不是只有文件）。
2. 有最小測試或 smoke 驗證命令。
3. 有回退策略（至少可回到上一穩定版本）。
