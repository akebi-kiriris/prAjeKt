# Phase 11：前端測試補強與專案健檢規劃

> 日期：2026-06-24  
> 狀態：已完成（含 11.9 最後錯誤邊界補強）  
> 詳細改善紀錄：`docs/learning/前端型別檢查與專案健檢改善紀錄.md`

---

## 1. 階段定位

Phase 11 將 2026-06-24 前後完成的前端型別檢查、依賴健檢、錯誤邊界修正、元件互動測試與 coverage 補強，正式收斂成一個可追蹤的工程階段。

本階段不是單純追求 coverage 80%，而是依序保護：

1. 高頻使用者流程
2. 高風險寫入與刪除操作
3. API 錯誤與失敗後的畫面狀態
4. Service、Store、Utils 與 View 之間的契約
5. CI 能穩定重跑的前端驗證基線

Phase 11 完成後，下一階段才進入跨前後端、資料庫與 Agent 主流程的 Integration Test。

---

## 2. 本階段目標

1. 建立可信的前端驗證指令與 CI 流程
2. 讓 coverage 計入實際產品 `.ts` / `.vue`，避免只測到測試檔本身
3. 補齊核心頁面、元件、Service、Store 與 Utils 測試
4. 補上成功、取消、失敗、權限、日期、空資料與非同步邊界
5. 讓 API 操作失敗時有使用者可見回饋，不只寫入 console
6. 保留測試改善紀錄，讓後續能理解為什麼補、補了什麼
7. 為 Phase 12 Integration Test 準備穩定的單元與元件測試地基

---

## 3. 本階段不做什麼

1. 不為了 coverage 數字測試純靜態模板
2. 不要求每個檔案都達到 100%
3. 不把所有 View 組成一個脆弱的大型整合測試
4. 不在本階段建立完整前後端 Integration Test 環境
5. 不建立 AI benchmark、評測報表或 merge gate
6. 不建立完整 Observability dashboard
7. 不因測試紅燈就直接改產品碼；先排除 selector、mock 與非同步等待問題

> 定位：只補目前仍具有明確使用者風險的錯誤與 Socket 邊界。這批不是為了把 coverage 推到特定數字，也不擴張成 Phase 12 的真實跨層整合測試。

#### 11.9.1 | CopilotDock 錯誤流程

目標檔案：

- `frontend/src/components/__tests__/CopilotDock.test.ts`

預計案例：

- [x] 規劃 API 失敗
  - `createAgentPlan` reject 後顯示解析過的錯誤 toast
  - planning 狀態結束，不顯示殘留 plan
  - 原始輸入保留，使用者可直接重試
- [x] 重提案 API 失敗
  - `replanAgent` reject 後保留原 `plan_id` 與原計畫
  - loading 狀態結束，不誤進入執行結果
  - 顯示「重提案失敗」或 API 回傳的具體訊息
- [x] 執行 API 失敗
  - `executeAgentPlan` reject 後保留待確認計畫，允許再次執行或放棄
  - 不產生假的成功結果
  - loading 狀態結束並顯示錯誤 toast
- [x] 放棄計畫 API 失敗
  - `rejectAgentPlan` reject 後不得清除目前計畫
  - 顯示錯誤並保留再次放棄或執行的可能
- [x] malformed step output
  - `step.output.data` 為 `null`、字串、陣列或缺少預期欄位時不可讓元件崩潰
  - 有 `output.error.message` 時顯示錯誤摘要
  - 缺少 task name / estimated days / result counters 時採安全 fallback
  - 不把 malformed item 渲染成空白或 `undefined`

Mock 原則：

- 沿用現有 `copilotService` 與 toast mocks。
- 每個案例只覆寫該次 API 行為，`beforeEach` 清理所有 mock。
- 優先從 DOM 觀察「計畫是否保留、結果是否出現、按鈕能否重試」，不直接斷言內部 ref。

#### 11.9.2 | groups store Socket 邊界

目標檔案：

- `frontend/src/stores/__tests__/groups.test.ts`

測試準備：

- [x] 擴充 `socketService.on*` mocks，捕捉實際註冊的 connect、disconnect、ready、group message、group error callback
- [x] 由測試主動觸發 callback，驗證 store 的公開 state 與 service 呼叫

預計案例：

- [x] 沒有 access token 時不建立 Socket 連線
  - `openChat` 仍可透過 HTTP 載入訊息
  - 不呼叫 `connect`、不 join room
- [x] 重複訊息去重
  - 相同 `message_id` 經 Socket 重送時只保留一筆
  - 新訊息仍依 `created_at` 穩定排序
- [x] 忽略其他群組訊息
  - `payload.group_id` 與目前群組不同時不得加入 messages
  - 尚未開啟群組時收到訊息也不得污染 state
- [x] disconnect 狀態清理
  - connect callback 將 `socketConnected` 設為 `true`
  - disconnect callback 將 `socketConnected`、`socketReady` 重設為 `false`
- [x] ready 與 Socket error 保存
  - 有效 `user_id` 將 `socketReady` 設為 `true`
  - group error 保存具體 `message`
  - 缺少訊息時使用「Socket 發生錯誤」fallback
- [x] destroySocket 完整解除
  - 已加入房間時先 leave room
  - 對每個已註冊 handler 呼叫對應 `off*`
  - 清除連線、ready、error 與 scroll callback 狀態

Mock 原則：

- 不啟動真實 Socket.IO server。
- store 單元測試只驗證事件註冊、狀態轉換、去重與 fallback；真實連線交給 Phase 12。

## 8. 與後續 Phase 的關係

- `Phase 12 - Integration Test`
  - 驗證 frontend / API / service / database / agent 的跨層主流程
- `Phase 13 - Evaluation`
  - 建立 Agent / AI / RAG benchmark、指標與回歸比較
- `Phase 14 - Observability`
  - 收斂 trace、metrics、error taxonomy 與操作追蹤

Phase 11 的責任是讓單點與元件層先可靠；Phase 12 才負責證明整條系統路徑能一起工作。
