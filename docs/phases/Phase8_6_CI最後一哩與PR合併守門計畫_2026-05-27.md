# Phase 8.6：CI 最後一哩與 PR 合併守門計畫

> 日期：2026-05-27  
> 範圍：`.github/workflows/*`、GitHub Branch Protection、PR 流程規範  
> 目標：把「有 CI」升級成「可控、可防呆、可安全合併」的工程守門流程

---

## 1. 現況判讀（目前已經有 CI）

目前 repo 已有兩條 workflow：

1. `backend-tests.yml`
2. `frontend-tests.yml`

代表「測試自動化」已存在。  
但 8.6 的重點不是從 0 到 1，而是做「1 到 1.5」：

1. 把 PR merge gate（required checks）設好。
2. 把 deploy 與 test 解耦（避免 PR/一般 push 誤觸發部署）。
3. 補上最小流程規範（PR -> checks -> merge）。

---

## 2. 本階段不做事項

1. 不引入複雜多環境發布（staging/prod matrix）。
2. 不導入重量級安全掃描平台（SAST/DAST 全套）。
3. 不重寫所有 workflow，只做必要收斂。

---

## 3. 目標交付（完成定義）

完成 8.6 視為達標需同時滿足：

1. `main` 分支設定 required checks（frontend + backend）。
2. PR 在 checks 全綠前不可 merge。
3. Deploy 僅在指定條件觸發（例如 `push main` 或手動 workflow_dispatch）。
4. 文件寫清楚團隊固定流程（開分支、PR、merge）。

---

## 4. 核心決策

## 4.1 測試與部署分離

建議把 frontend workflow 拆成：

1. `frontend-ci.yml`：只跑 `npm ci`、`npm run test:coverage`、`npm run build`
2. `frontend-deploy.yml`：只處理部署（限定 `push main` 或手動）

避免每次 PR 測試成功就自動 deploy。

## 4.2 PR 為主、禁止直推 main

建議流程固定為：

1. feature branch 開發
2. 開 PR 到 `main`
3. checks 全綠 + review 完成
4. merge

---

## 5. 實作步驟

## Step 1：Workflow 收斂

1. backend workflow 保留測試用途
2. frontend workflow 移除自動部署步驟（或拆成 deploy 專用檔）
3. 視需要把 `guardrails:payload` 併入 frontend CI

## Step 2：GitHub Branch Protection

`main` 建議啟用：

1. Require a pull request before merging
2. Require status checks to pass before merging
3. Required checks：
 - Backend Tests
 - Frontend Tests（或 Frontend CI）
4. Restrict who can push to matching branches（避免直接 push main）

## Step 3：PR 模板與最小規範

新增 `.github/pull_request_template.md`，最少包含：

1. 變更摘要
2. 風險評估
3. 測試證據（貼指令與結果）
4. 回滾方式

---

## 6. 驗證方式

## 本地驗證

1. `backend`: `venv\Scripts\python.exe -m pytest`
2. `frontend`: `npm run test:coverage`、`npm run build`

## GitHub 驗證

1. 建一個測試 PR
2. 確認 required checks 正確顯示
3. 刻意讓一個 check fail，確認 PR 無法 merge
4. checks 全綠後確認可 merge

---

## 7. 建議的固定開發流程（之後照這個走）

1. 從 `main` 切 branch（例如 `feature/phase8-6-ci-hardening`）
2. 本地測試通過後 push branch
3. 開 PR
4. 等 CI 全綠
5. review 後 merge 到 `main`
6. deploy 由 `main` push 或手動觸發

---

## 8. 風險與對策

1. 風險：workflow 名稱變更導致 required checks 對不上  
對策：先建立新 workflow，再去 Branch Protection 重新勾選新名稱。

2. 風險：deploy 被搬走後，團隊以為「沒自動上線」是壞掉  
對策：在 README/進度追蹤註記 deploy 觸發條件改為 `push main` 或手動。

3. 風險：PR 流程初期感覺變慢  
對策：保留最小檢查集，先求穩定，再逐步增加 guardrails。
