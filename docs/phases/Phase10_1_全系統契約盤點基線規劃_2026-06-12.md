# Phase 10.1：全系統契約盤點基線

> 日期：2026-06-12  
> 目的：把 Learnlink 目前真正有前後端耦合的主模組，整理成一份可維護的契約地圖，並先修掉幾個明顯的 response shape / payload 鬆動點。  
> 定位：10.1 不是全量文件化，也不是直接導入 OpenAPI；它是 10.2 / 10.3 收斂工作的基線。

---

## 1. 本次盤點結論

10.1 盤完後，可以先下三個結論：

1. 系統目前的契約主體已經集中在 `backend/blueprints/*` + `frontend/src/services/*` + `frontend/src/types/*`，但仍有少量「前端假設的 response shape」與後端實際回傳不一致。
2. 高風險區不是只有 agent，而是 `tasks`、`timelines/knowledge`、`groups/messages/notifications` 這幾條經常被 UI 直接消費的主線。
3. 目前最需要的不是先導 Swagger，而是先把 schema 來源、response envelope、frontend type 這三層對齊，再考慮輸出成 OpenAPI。

## 3. 全系統契約地圖

## 3.1 auth / profile

- 後端入口
  - `backend/blueprints/auth.py`
  - `backend/blueprints/profile.py`
- 前端入口
  - `frontend/src/stores/auth.ts`
  - `frontend/src/services/profileService.ts`
  - `frontend/src/types/profile.ts`
- 契約特性
  - `auth` 前端目前沒有獨立 `authService.ts`，而是由 `auth store` 直接呼叫共用 `api.ts`
  - `profile` 已有獨立 service/type，契約相對穩定
- 主要 response shape
  - `POST /auth/register` -> `{ message, user_id }`
  - `POST /auth/login` / `POST /auth/refresh` -> token envelope
  - `GET /auth/me` / `GET /profile/me` -> user/profile object
  - `PUT /profile/me` -> `{ message }`
- 測試守護
  - auth flow 主要靠 store / component 流程與既有 backend blueprint/service 測試，不是集中在 service 契約測試
- 風險判斷
  - 穩定度：中高
  - 風險點：`auth` 沒有獨立 service 層，之後若要 OpenAPI 對接，需要先決定是否保留「store 直打 api」模式

## 4. 本次 10.1 已完成的對齊修正

本輪已直接修掉的高噪音契約點：

1. `taskService.createSubtask()` / `toggleSubtask()` 的 response 型別與 UI 消費點對齊
2. `taskService` 在 `create/update` 內補 `tags` 正規化，避免前端字串直接撞上後端 `list[str]`
3. `groupService.create/join/leave/sendMessage` 回傳型別改成真實 envelope
4. `GroupsView.vue` 拿掉 create-group 的 unsafe cast
5. `notificationService` / `trashService` / `todoService` / `timelineService` 多個 mutation API 的回傳型別從 `void` 對齊為 `{ message }`
6. `copilot` 前端型別補上 `request_id` / `trace`

這些調整的原則都是一樣的：

- 不改後端行為
- 先把前端 service/type 拉回「真實契約」
- 讓後面做 schema 收斂時，不用先清一輪假型別

## 5. 第一版高風險清單

目前優先度最高的風險不是「端點最多的模組」，而是「契約語義最容易漂移的模組」：

1. `tasks`
   - `tags` 有 UI string / API list 的雙重語義
   - comment / file / subtask 子資源多，response shape 容易被前端扁平假設
2. `timelines + knowledge`
   - 同一支 frontend service 承載多條語義線
   - AI / knowledge / CRUD / member API 夾在一起
3. `copilot / agent`
   - payload 與 trace 仍在演進
   - 單一 API response 可能同時包含 domain result 與 observability metadata
4. `groups / notifications`
   - REST 與 socket event payload 並存
   - UI 常直接消費回傳值

## 6. 10.2 / 10.3 的直接接續建議

10.1 做完後，下一步不建議立刻導 OpenAPI 套件，而是先做下面這些：

1. 先把 backend request / response schema 的來源邊界定清楚
   - blueprint payload
   - response serializer
   - service/domain guard
2. 明確切分 frontend 的兩種型別
   - UI form model
   - API payload / response model
3. 先挑 `tasks`、`timelines/knowledge`、`copilot` 做第一批 schema 收斂
4. 等 schema 來源比較穩，再評估要不要接 `APIFlask` / `flask-smorest` 或只做契約匯出
