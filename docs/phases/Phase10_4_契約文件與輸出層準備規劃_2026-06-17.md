# Phase 10.4：契約文件與輸出層準備規劃

> 日期：2026-06-17  
> 主旨：在 Phase 10.3 已完成主要 backend response contract、frontend consumer 主線對齊與第一版 OpenAPI 入口後，進一步補齊「閱讀版契約索引」、「文件維護原則」與「OpenAPI 輸出層維護流程」，讓契約不只存在於程式內，也能被穩定查閱、追蹤與維護。  
> 定位：10.4 不是再做一輪 request / response 大重構；它是把 10.1 ~ 10.3 已收斂出的真相來源，整理成可持續維護的文件與輸出層規則。  
> 前提：`backend/contracts/` 已正式定版為後端契約真相來源，`docs/reference/openapi.json` 與 `/api/openapi.json` 已能輸出第一版文件，10.3 的 protected fields 與 frontend 不可自送欄位說明也已補齊。

---

## 1. 為什麼 10.4 要接在 10.3 後面

10.3 解決的是：

1. backend response contract 不再只是靠印象維護
2. frontend 主要 consumer 不再優先靠猜測對接
3. 第一版 OpenAPI 已能從既有契約輸出

但現在還缺的是：

1. 哪些 API 已穩定、哪些仍在重構期，沒有一份閱讀版索引可快速查
2. 文件與程式之間的主從關係雖然已經有共識，但還沒被明確寫成維護原則
3. OpenAPI 已能輸出，但「什麼時候要更新、更新後怎麼檢查、缺口怎麼標」還沒正式定義

如果這一層不補，後面很容易變成：

- 程式內契約已收斂，但閱讀者還是得翻 route / service / tests 才知道哪裡是最新
- OpenAPI 存在，但久了之後不知道它是不是還可信
- 文件更新變成額外負擔，而不是依附真相來源的維護流程

所以 10.4 的目的，是把 10.3 長出的契約成果，整理成「可閱讀、可檢查、可維護」的輸出層。

---

## 2. 10.4 要回答的核心問題

10.4 應至少回答：

1. 目前哪些 API 已有穩定 request / response schema？
2. 哪些 API 的真相來源已明確落在 `backend/contracts/`？
3. 哪些 API 已反映到 OpenAPI，哪些仍屬暫時缺口？
4. 文件與程式發生差異時，應該以哪一層為準？
5. 後續每次改主要 API，文件與輸出層要一起做哪些檢查？
6. 不同 endpoint 的「穩定、部分穩定、動態、二進位回應、歷史彈性」狀態要如何標記？

---

## 3. 本階段範圍

10.4 這一輪範圍建議收在三塊：

1. 閱讀版契約索引
2. 文件維護原則
3. OpenAPI 輸出與維護流程

會引用的現有成果包括：

1. `backend/contracts/`
2. `docs/reference/backend_契約來源索引.md`
3. `docs/reference/openapi.json`
4. `backend/openapi_document.py`
5. `docs/reference/Phase10_3_後端回應契約收斂實作整理_2026-06-17.md`
6. `docs/reference/Phase10_3_protected_fields_與_frontend_不可自送欄位說明_2026-06-17.md`

這一輪不再去做：

1. 新一波 request contract 大搬動
2. 新一波 response contract 全面重構
3. 新一輪 frontend consumer 大掃除
4. 把 OpenAPI 改成完全自動從所有 Pydantic model 推導的工具化工程

## 4. 10.4 的收斂順序

### 4.1 先補閱讀版契約索引

先產出一份適合人看的索引，但不要重寫 `docs/reference/backend_契約來源索引.md`。

既有 `backend_契約來源索引.md` 已負責指出各模組的契約來源、guard、tool contract 與 OpenAPI 入口；10.4 要補的是更偏「維護狀態」的閱讀版矩陣，讓人能快速判斷某個 API 目前可不可信、是否已反映到 OpenAPI、是否還有刻意保留的彈性。

這份閱讀版索引至少標出：

1. 哪些 API 已有穩定 request schema
2. 哪些 API 已有穩定 response contract
3. 哪些 API 已有 focused tests 守護
4. 哪些 API 已反映到 OpenAPI
5. 哪些仍屬重構中或刻意保留彈性的區塊

這份索引的定位不是重新定義契約，也不是第二份手工 API 規格書，而是把目前真相來源整理成方便查閱的維護狀態入口。

### 4.2 補上契約狀態分類

閱讀版索引需要先定義狀態值，避免每個模組用不同說法描述成熟度。

建議至少使用：

1. `stable`
   - request schema、response contract、OpenAPI、focused tests 都已有基本對齊
   - 後續變更時應視為契約變更，需要同步檢查 consumer
2. `partial`
   - 部分 request / response 已契約化，但仍有 endpoint 或欄位由 service / route 承諾
   - 後續應列入 10.5 / 10.6 的殘留鬆動點盤點
3. `dynamic`
   - payload 本質上仍保留彈性，例如 `copilot / agent` 的 tool-specific result、trace metadata、tool payloads
   - 文件應如實標記為 dynamic，不為了讓 OpenAPI 好看而硬寫假穩定 schema
4. `binary`
   - file download / preview 這類非 JSON response
   - 應在 OpenAPI 用 binary response 表示，不放進 JSON response contract
5. `legacy-flexible`
   - 為了維持既有 frontend shape 或歷史 API 行為，暫時保留的彈性外型
   - 文件應記錄原因與後續是否需要收斂，而不是默默放著

### 4.3 再定義文件維護原則

要明確寫清楚：

1. 文件不是新的真相來源
2. 程式內的 schema / contract / tests 仍是主體
3. 閱讀版文件與 OpenAPI 是輸出層
4. 若文件與程式不一致，先回頭修真相來源或輸出邏輯，不手動讓文件漂移成另一套現實

這段應至少涵蓋：

1. 何時要更新文件
2. 何時要更新 OpenAPI
3. 何時只需要更新索引，不需要新增新文件
4. 哪些變更一定要同步檢查前端 type / response shape / OpenAPI
5. 哪些缺口只需要標記為 `dynamic` / `binary` / `legacy-flexible`，不應在 10.4 硬重構

### 4.4 最後收斂 OpenAPI 維護流程

OpenAPI 這輪不追求「最炫的產生方式」，只追求：

1. 更新方式明確
2. 差異可追
3. 缺口有記錄
4. 能持續和 `backend/contracts/` 對齊

至少應補清楚：

1. `/api/openapi.json` 與 `docs/reference/openapi.json` 的關係
2. 靜態檔應在 `backend/` 目錄下用 `.\venv\Scripts\python.exe scripts/export_openapi.py` 重新匯出
3. 匯出目標是 repo 內的 `docs/reference/openapi.json`
4. 何時需要重新匯出靜態檔
5. 匯出後要檢查哪些重點
6. 哪些 endpoint 若仍用 generic object / dynamic payload，應如何標記而不是假裝已完全定版

## 5. 這一輪建議的實作策略

### 5.1 閱讀版契約索引

建議文件至少要有這幾欄：

1. 模組名稱
2. 主要 API
3. request schema 來源
4. response contract 來源
5. OpenAPI 狀態
6. focused test 狀態
7. 契約狀態
8. 備註 / 特例

模組至少先覆蓋：

1. `auth / profile`
2. `tasks`
3. `timelines`
4. `knowledge`
5. `groups / messages / notifications`
6. `todos / trash`
7. `copilot / agent`

建議矩陣欄位格式：

| 模組 | API / 流程 | request schema | response contract | OpenAPI | focused tests | 狀態 | 備註 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| tasks | `POST /tasks` | `TaskCreateRequest` | `TaskIdMutationResponse` | 已覆蓋 | 已覆蓋 | `stable` | mutation response 維持既有 shape |
| knowledge | download / preview | 不適用 | binary response | 已覆蓋 | 視測試現況標記 | `binary` | 不放進 JSON response contract |
| copilot / agent | plan / execute / replan | 已知外層 request | tool / agent payload | 部分 generic object | 視測試現況標記 | `dynamic` | 不硬包成假穩定 schema |

### 5.2 文件維護原則

建議整理成簡短但可執行的規則，例如：

1. 先改 backend contract / route / tests，再更新閱讀版文件
2. 變更主要 API 時，至少同步檢查 frontend type、OpenAPI 與契約索引
3. 動態 payload 要如實標記，不假裝已完全 schema 化
4. phase 實作整理與閱讀版索引分工要清楚，不互相重覆抄寫
5. 若閱讀版文件與程式碼不一致，優先修 `backend/contracts/`、service payload、route 實作、OpenAPI 輸出或測試，不讓文件獨立漂移

最小檢查清單：

1. 若改 backend request / response contract，確認對應 focused backend tests
2. 若改 API response shape，確認 frontend `types/`、`services/`、store / component consumer 是否需要同步
3. 若改主要 API 或 schema，重新匯出 `docs/reference/openapi.json`
4. 若 endpoint 保留動態 payload，在閱讀版索引與 OpenAPI 缺口清單中標記狀態
5. 若只是補說明，不改真相來源，避免新增另一套欄位定義

### 5.3 OpenAPI 維護流程

建議至少補出：

1. 匯出指令
2. 匯出時機
3. 最低檢查項
4. 常見缺口處理方式

目前固定匯出方式：

1. 進入 `backend/`
2. 執行 `.\venv\Scripts\python.exe scripts/export_openapi.py`
3. 確認輸出檔為 `docs/reference/openapi.json`

例如：

1. 新增或修改主要 request / response schema 後重新匯出
2. 檢查主要 path 是否仍存在
3. 檢查關鍵 response schema ref 是否沒斷
4. 檢查 security scheme / multipart / binary response 是否仍正確
5. 檢查 `copilot / agent` 等 dynamic payload 是否被清楚標成 generic object / dynamic，而不是誤標成 stable

---

## 6. 本階段不做什麼

1. 不把閱讀版契約索引寫成第二份手工 API 規格書
2. 不讓 OpenAPI 反過來主導 backend contract 設計
3. 不因為文件整理而再重做一次 10.3 已完成的 response 收斂
4. 不把 `copilot / agent` 動態 payload 硬包成假穩定 schema，只為了讓文件好看
5. 不把 phase 規劃、實作整理、閱讀版索引三者混成一份超長文件

---

3. 一份 OpenAPI 維護流程說明

## 8. 完成標準

10.4 完成時，至少應該能回答：

1. 新人或未來的自己，能否不翻整個 backend 就快速定位主要 API 契約來源？
2. 文件與程式若有衝突，是否已清楚定義以哪一層為準？
3. OpenAPI 是否已從「只是有個輸出檔」提升成「有基本維護流程的輸出層」？
4. 哪些 API 已穩定，哪些仍保留動態或過渡狀態，是否已明確標記？
5. `docs/reference/openapi.json` 的更新指令、更新時機與檢查項是否已可被照著執行？
6. OpenAPI 缺口是否已被明確列出，而不是散在 phase 實作整理裡？

### 至少要達到的狀態

1. 閱讀版文件可用，但不搶真相來源角色
2. OpenAPI 可維護，但不被誤當成唯一規格書
3. 契約更新時，文件回寫與輸出層更新有最小固定流程
4. Phase 10 後半段開始從「收斂實作」進入「收斂維護方式」
5. 動態、二進位與歷史彈性 API 有明確標記，不被誤算成漏做或已完全定版

## 9. 和後續 10.5 / 10.6 的關係

10.4 做完後，10.5 才比較適合補：

1. 模組別主線導覽
2. 哪些流程最不穩
3. 哪些跨層風險仍值得單獨盤點

而 10.6 才更適合做：

1. 契約差異表
2. 剩餘鬆動點清理
3. 最終可穩定維護狀態確認

也就是說：

1. 10.3 收主線契約
2. 10.4 收文件與輸出層
3. 10.5 / 10.6 再做模組導覽與殘留鬆動點清理

## 10. 一句話版

10.3 收掉的是「後端 response 與前端 consumer 主線對齊」，  
10.4 要收掉的是「這些契約成果怎麼被查、被讀、被維護、被輸出」。  

順序應該是：

**先整理閱讀版契約索引，再定文件維護原則，最後收斂 OpenAPI 維護流程。**
