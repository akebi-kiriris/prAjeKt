# Phase 10.6：已知鬆動點實作清理規劃

> 日期：2026-06-18  
> 主旨：接續 10.4 契約狀態矩陣與 10.5 模組別主線導覽，只針對已標記的高價值鬆動點做小批量實作清理。  
> 定位：10.6 不是重新盤點整個系統，也不是另一輪全面 contract refactor；它是把已知可能造成 runtime drift、型別漂移或維護成本偏高的區塊逐批收斂。  
> 來源：`docs/reference/Phase10_4_契約文件與OpenAPI維護整理_2026-06-18.md`、`docs/reference/Phase10_5_模組別主線導覽整理_2026-06-18.md`

---

## 1. 為什麼需要 10.6

10.1 ~ 10.4 已完成契約盤點、後端 contract 收斂、response / OpenAPI / frontend consumer 主線對齊與維護文件；10.5 也把主要模組的閱讀路線補起來。

但 10.4 / 10.5 同時留下幾種「不是立即 bug，但容易讓後續維護變慢」的鬆動點：

1. frontend service 邊界和模組語意不完全一致
2. AI / RAG / snapshot / tool result 這類 payload 有些地方穩定，有些地方仍需要保留 dynamic
3. REST / socket 或 test mock 裡可能還有命名與型別漂移
4. legacy-flexible list endpoint 需要明確保留理由，避免未來誤以為是漏做

10.6 的任務，是把這些已知點逐批判定、整理、必要時實作；每一批都要能說清楚「為什麼現在值得做」與「做到哪裡就該停」。

---

## 2. 本階段目標

10.6 要完成的不是一份更大的盤點表，而是可執行的清理節奏：

1. 將 10.4 / 10.5 的候選檢查點整理成優先順序
2. 對每個候選點做「實作清理 / 文件標記 / 延後」判定
3. 只對已穩定、會降低 drift 風險的 shape 補 contract / type / test
4. 保留仍需要彈性的 `dynamic`、`binary`、`legacy-flexible` 區塊，並把原因寫清楚
5. 每完成一批，回寫契約狀態矩陣、模組導覽、OpenAPI 靜態檔與 focused tests

---

## 3. 本階段不做什麼

10.6 明確不做：

1. 不重新全系統 contract 盤點
2. 不把所有 endpoint 改成統一 envelope
3. 不為了 OpenAPI 好看而硬包 AI / tool / trace dynamic payload
4. 不重寫 timeline / knowledge / copilot 的主要功能流程
5. 不建立完整 OpenAPI 與 frontend type 自動差異檢查
6. 不做 Phase 11 integration tests 的主體內容
7. 不把 10.7 的最小護欄與自動化準備提前塞進 10.6

如果某個項目只是「看起來可以更整齊」，但不會實際降低 drift、閱讀成本或測試盲點，就先不做。

## 4. 優先順序

### 4.1 第一批：frontend service 邊界與高頻 consumer

優先檢查 `timelineService.ts` 是否應拆出 `knowledgeService.ts`。

> 2026/06/19 更新：第一批已完成。knowledge documents API 已拆至 `frontend/src/services/knowledgeService.ts`，`timelineService.ts` 回到 timeline 主線；`KnowledgeBaseView.vue` 與 `TimelineDetailDialog.vue` 已改用新 service。

判定方向：

1. 如果 knowledge API 已被個人知識庫頁與 timeline project files 共同使用，且 import 語意持續讓人誤解，優先拆出 `knowledgeService.ts`
2. 如果拆分會造成大量 consumer churn，先保留現狀，但在 `timelineService.ts` 或 reference 文件明確標記歷史原因
3. 拆分時不得改變 backend API shape，也不得順手重構 knowledge 權限流程

可能影響範圍：

1. `frontend/src/services/timelineService.ts`：已移除 knowledge API
2. `frontend/src/services/knowledgeService.ts`：已新增 knowledge documents API wrapper
3. `frontend/src/views/KnowledgeBaseView.vue`：已改用 `knowledgeService`
4. `frontend/src/components/timelines/TimelineDetailDialog.vue`：project files 已改用 `knowledgeService`
5. `frontend/src/services/__tests__/timelineService.test.ts`：已移除 knowledge endpoint assertions
6. `frontend/src/services/__tests__/knowledgeService.test.ts`：已新增 endpoint mapping tests
7. `frontend/src/views/__tests__/KnowledgeBaseView.test.ts`：已改 mock `knowledgeService`
8. `frontend/src/components/timelines/__tests__/TimelineDetailDialog.phase7.test.ts`：已補 `knowledgeService` mock

驗收標準：

1. [x] knowledge API 的 import 路徑語意清楚
2. [x] Timeline 主線仍可透過 project files 操作 knowledge documents
3. [x] 個人知識庫頁不需要知道 timeline service 的歷史包袱
4. [x] focused frontend tests 通過

### 4.2 第二批：timeline AI generate / suggest plan schema 判定

檢查 AI generate tasks 與 RAG suggest plan 的 request / response 是否還有穩定子集合可細分。

> 2026/06/19 更新：第二批已完成判定。`timeline_contracts.py` 已有 `TimelineGenerateTasksResponse`、`TimelineGeneratedTaskResponse`、`TimelinePlanSuggestionResponse` 與 source reference / meta / suggested task 等 named schema；`frontend/src/types/timeline.ts` 也已有對應型別。本批不新增第二套 schema，避免把同一份穩定契約拆出重複來源。

判定方向：

1. 已穩定且 frontend 明確依賴的欄位，可以補 named schema 或更細 frontend type
2. prompt、fallback、LLM intermediate data 不硬 schema 化
3. `ai-suggest-plan` 入口仍以 `rag_planning_service.py` 的實際輸出為準

可能影響範圍：

1. `backend/contracts/timeline_contracts.py`
2. `backend/blueprints/timelines.py`
3. `backend/services/rag_planning_service.py`
4. `backend/openapi_document.py`
5. `frontend/src/types/timeline.ts`
6. `frontend/src/services/timelineService.ts`

驗收標準：

1. [x] 已穩定欄位不再靠猜測消費
2. [x] 仍需要彈性的 AI payload 被明確標記為 dynamic 或保留現狀
3. [x] OpenAPI schema ref 已維持既有 named schema，無需新增重複模型

### 4.3 第三批：groups / messages / notifications payload 差異清理

檢查 group snapshot `summary`、message REST / socket payload、notification list guard。

> 2026/06/19 更新：第三批已完成。group snapshot `summary` 已新增 named schema，`GroupSnapshotJobResponse.snapshot` 也改為 `GroupSnapshotResponse | None`；message REST / socket 維持既有共用 serializer；notification list 短期保留 legacy-flexible list shape。

判定方向：

1. snapshot `summary` 若內層結構已穩定，補 named schema；若仍受 LLM / digest 內容影響，維持 dict 並更新文件說明
2. message REST / socket 若有欄位命名差異，先確認是否由共用 serializer 保證
3. notification list 若 frontend guard 不足，只補會防止真實 drift 的 guard，不補形式化包裝

可能影響範圍：

1. `backend/contracts/group_contracts.py`
2. `backend/services/group_service.py`
3. `backend/services/message_service.py`
4. `frontend/src/types/group.ts`
5. `frontend/src/stores/groups.ts`
6. `frontend/src/stores/notifications.ts`

驗收標準：

1. [x] REST / socket 欄位命名差異若存在，要有明確原因或修正
2. [x] snapshot summary 已可標為穩定 API schema；LLM 原始輸入仍只在 service normalize 前保持彈性
3. [x] frontend guard 只補在主要 consumer 會受影響的位置

### 4.4 第四批：copilot / agent tool result 穩定子集合

檢查 tool-specific result、plan / execute dynamic payload、trace metadata 是否有穩定外層可契約化。

> 2026/06/19 更新：第四批已完成。`tool_outputs.py` 已讓 timeline AI generate / batch create / conflict check、group snapshot、knowledge upload/list、task comment summary 這些常用 tool result 接上既有 response model；Copilot plan / trace metadata / planner intermediate data 仍維持 dynamic。

判定方向：

1. tool list、tool envelope、常用 tool result 的穩定外層優先
2. trace metadata、planner intermediate data、tool payloads 若仍彈性，維持 dynamic
3. 高副作用工具 retry / protected field 規則若需要整理，先補差異表或文件，不急著重構流程

可能影響範圍：

1. `backend/contracts/tool_inputs.py`
2. `backend/contracts/tool_outputs.py`
3. `backend/contracts/tool_envelopes.py`
4. `backend/services/copilot_service.py`
5. `backend/services/agent_plan_service.py`
6. `frontend/src/types/copilot.ts`
7. `frontend/src/components/copilot/CopilotDock.vue`

驗收標準：

1. [x] 穩定外層有 contract / frontend type 對應
2. [x] dynamic payload 不被假裝成 fully stable
3. [x] trace metadata 的保留策略在 reference 文件中可追

### 4.5 第五批：tests mock cast 與 legacy-flexible 判定

最後處理 frontend tests 內部 mock cast 與 list endpoint 的 `legacy-flexible` 狀態。

> 2026/06/19 更新：第五批已完成。`TimelineSubcomponents.test.ts` 的純 fixture `as any` 已改為 `satisfies` domain types，並補正 `KnowledgeDocumentItem.chunk_count` 可為 `null`；service mock cast 維持測試輔助型別，不列為 contract drift。legacy-flexible list endpoint 短期保留，未來若統一 envelope 需另開 API 變更計畫。

判定方向：

1. 會遮蔽真實 contract drift 的 cast 要移除或改成具名 test fixture
2. 只是測試輔助型別的 cast 可以保留，但要有理由
3. list endpoint 短期不統一 envelope；若未來要統一，另開 API 變更計畫

驗收標準：

1. [x] focused tests 不再靠過度寬鬆 mock 掩蓋 response shape
2. [x] `legacy-flexible` endpoint 保留原因寫在 10.4 矩陣或相關 reference
3. [x] 沒有為了統一外觀而破壞既有 frontend consumer

## 5. 每批實作流程

每一批都照同一個流程走：

1. 從 10.4 矩陣和 10.5 主線導覽確認候選點
2. 讀實際 route / service / contract / frontend consumer，不只看文件
3. 判定為 `實作清理`、`文件標記` 或 `延後`
4. 若實作，先改真相來源，再改輸出層與 consumer
5. 補或更新 focused tests
6. 若 OpenAPI 有 schema / path / dynamic 標記變更，重新匯出 `docs/reference/openapi.json`
7. 更新 reference 文件與進度文件
