# Phase 9.5 Agent 契約一致性與安全邊界補強計畫

日期：2026-06-05  
階段定位：Phase 9.5 後續補強  
目標：收斂 Agent 主線在 `plan / replan / execute` 契約、Tool 邊界、防禦式狀態讀取，以及舊 service 被 Agent 直接調用後的權限風險。

---

## 一、這份計畫要解決什麼

這一波不是要重做 Agent 架構，而是針對已完成的 Phase 9.3 ~ 9.5 主線，補上幾個「現在方向正確，但保護還不夠密」的地方。

重點有四類：

1. 前後端 Agent payload 契約還沒完全對齊
2. Tool Registry 邊界仍可再補最後一道錯誤保護
3. LangGraph state 讀取有少數地方過度樂觀
4. 舊有 task / timeline service 原本依賴 blueprint guard，Agent 化後應逐步補 service 內權限檢查

這些問題不是全部都要立刻做，但如果不整理，很容易在後續擴充選項式 Agent、更多工具、或多人使用時踩坑。

---

## 二、範圍界定

這次只做「補強」，不做下列事情：

1. 不重寫 Agent graph
2. 不將 `AgentPlanStore` 直接改成 DB-backed
3. 不全面搬移所有 blueprint payload model
4. 不一次收斂所有 `dict[str, Any]` output schema
5. 不大改前端 Agent 面板版面

也就是說，這次是：

1. 修契約
2. 補邊界
3. 補測試
4. 為之後的 Phase 9.6 / Phase 10 打底

---

## 三、問題分級

## P0：現在就值得修

### 1. `plan / replan / execute` 的 `tool_payloads` 契約不一致

- [x] 已完成（2026-06-05）

現況：

1. 後端 `/agent/plan` 支援 `tool_payloads`
2. 後端 `/agent/replan` 尚未將 `tool_payloads` 傳入 `create_copilot_agent_plan()`
3. 前端 `CopilotAgentPlanPayload` 尚未定義 `tool_payloads`
4. 前端 `CopilotAgentReplanPayload` 尚未定義 `tool_payloads`
5. 前端 `CopilotAgentExecuteByPlanPayload` 仍允許 `tool_payloads`
6. 後端 execute 階段明確拒絕 `tool_payloads` override

風險：

1. replan 時可能遺失前端準備好的工具參數
2. 前端 type 與後端行為不一致
3. 後續做選項式 Agent 時，契約會持續混亂

要做的事：

1. `backend/blueprints/copilot.py`
   - `/agent/replan` 補接 `tool_payloads`
2. `frontend/src/types/copilot.ts`
   - `CopilotAgentPlanPayload` 補 `tool_payloads`
   - `CopilotAgentReplanPayload` 補 `tool_payloads`
   - `CopilotAgentExecuteByPlanPayload` 移除 `tool_payloads`

---

### 2. Tool Registry 應補 handler exception boundary

- [x] 已完成（2026-06-05）

現況：

1. `execute_registered_tool()` 已統一做 `input_model` 驗證
2. 但 handler 執行例外主要仍依賴各 handler 自己 `try/except`

風險：

1. 未來若新增 handler 忘記包錯誤
2. 例外可能直接炸出 Agent graph
3. `route_by_error` 無法穩定依 `error_code` 路由

要做的事：

1. `backend/services/tools/registry.py`
   - 在 `tool.handler(validated_payload)` 外再包一層 `try/except`
   - 一律透過 `map_exception_to_tool_error()` 回傳 failure envelope

---

### 3. `agent_nodes.py` 對 step 結構的讀取要改成防禦式

- [x] 已完成（2026-06-05）

現況：

1. `_extract_generated_tasks_from_state()` 直接用 `step["tool_name"]`
2. `finalize_node()` 直接用 `steps[-1]["output"]`

風險：

1. 目前主線雖大多安全
2. 但未來只要多插一個 node、人工確認步驟、或 malformed state
3. 很容易因為 `KeyError` 直接 500

要做的事：

1. `backend/chains/agent_nodes.py`
   - 改用 `step.get("tool_name")`
   - `finalize_node()` 讀取最後一步時要先檢查型別

---

### 4. `create_notification()` 不應完全吞掉例外

- [x] 已完成（2026-06-05）

現況：

1. 通知失敗不影響主流程，這個方向是對的
2. 但現在 `except Exception: pass`

風險：

1. 通知系統壞掉時很難追
2. debug 時沒有任何可見訊號

要做的事：

1. `backend/services/task_service.py`
   - 保持「不影響主流程」
   - 但至少補 warning log

---

### 5. `TaskCreateInput` mutable default list 要修正

- [x] 已完成（2026-06-05）

現況：

1. `assignee_user_ids: list[int] = []`
2. `depends_on_task_ids: list[int] = []`

風險：

1. 這是典型不乾淨寫法
2. 雖然 Pydantic v2 幫忙不少，但仍不建議保留

要做的事：

1. `backend/services/contracts/task_contracts.py`
   - 改成 `Field(default_factory=list)`

## P1：下一波建議補強

### 6. planner prompt 要明講 protected keys 不可由模型填

- [x] 已完成（2026-06-05）

現況：

1. `tool_plan_service.py` 會把完整 input schema 提供給模型
2. schema 內含 `user_id`、`timeline_id`、`task_id`、`group_id` 等 scope 欄位
3. 後端雖然會 sanitize，但模型不知道這件事

風險：

1. 模型提案與實際可執行 payload 有落差
2. 增加 replan / debug 的認知成本

要做的事：

1. `backend/services/tool_plan_service.py`
   - prompt 補上規則：
     - 不可在 `payload_draft` 中填入 `user_id / actor_user_id / created_by / timeline_id / task_id / group_id`
     - 這些欄位由系統 context 注入

---

### 7. planner steps 長度應設上限

- [x] 已完成（2026-06-05）

現況：

1. `tool_plan_service.py` 驗證 steps 是否為非空 list
2. 但未限制最多幾步
3. execute 端仍有 `max_loops`

風險：

1. 使用者確認的 plan 和實際執行上限可能不一致
2. 長步驟提案會讓 UX 與 trace 變得模糊

要做的事：

1. `backend/services/tool_plan_service.py`
   - 為 plan steps 設定上限
2. 建議做法：
   - 超過上限直接 raise，而不是偷偷截斷

---

### 8. `ToolSuccess / ToolFailure` 的 `ok` 欄位收斂為 Literal

- [x] 已完成（2026-06-05）

現況：

1. `ok: bool = True`
2. `ok: bool = False`

風險：

1. 若未來有人直接建立 model，仍可能產生語意不一致資料

要做的事：

1. `backend/services/contracts/tool_envelopes.py`
   - `ok: Literal[True]`
   - `ok: Literal[False]`

---

### 9. `tool_outputs.py` 先收斂 Agent 會串接的輸出

現況：

1. 很多 output 仍是 `dict[str, Any]`
2. 目前先做 envelope 是合理的
3. 但後續若 Agent 要穩定讀結果，output schema 還是要逐步硬化

優先目標：

1. `CreateTimelineToolOutput`
2. `TimelineGenerateTasksToolOutput`
3. `TimelineBatchCreateTasksToolOutput`
4. `TaskCommentSummaryToolOutput`

## P2：中期工程債與安全邊界

### 10. 寫入型 service 逐步補 `operator_user_id`

- [x] 本輪已先完成 `update_task_for_member` / `update_timeline_for_member`（2026-06-05）

這是這一波最值得正式記錄的中期風險。

現況：

1. 舊 REST 路徑大量依賴 blueprint decorator 做權限保護
2. 例如：
   - `require_task_role`
   - `require_timeline_role`
3. 但 Agent / Tool Registry 會直接走 service / handler，不一定會經過 blueprint guard

目前觀察：

1. `update_task_for_member(task_id, data)` 本身沒有 `operator_user_id`
2. `update_timeline_for_member(timeline_id, data)` 本身沒有 `operator_user_id`

風險：

1. 這不是單純重複驗證問題
2. 這是 Agent 化後 service 邊界需要重新定義的安全議題

要做的事：

1. 後續逐步將寫入型 service 改成：
   - `update_task_for_member(task_id, operator_user_id, data)`
   - `update_timeline_for_member(timeline_id, operator_user_id, data)`
2. service 內自己做 membership / role 驗證
3. handler 只能從 context 注入 actor，不信任外部 payload

這條不建議在本次與 P0 混做，但應正式列入後續 phase。

---

### 11. `Task / Timeline` 契約與驗證分散，後續要收斂

現況：

1. blueprint 有 payload model
2. service contracts 有一份
3. service 內又有白名單、normalize、日期 parse

判斷：

1. 這是工程債，方向上值得做
2. 但不適合和 Agent 主線補強混成一包

後續方向：

1. blueprint 只做 JSON / auth / route guard
2. contracts 做格式與欄位契約
3. service 做業務規則與權限

## 四、建議實作順序

### 第一批：先收 Agent 契約與邊界

1. `copilot.py`
   - `/agent/replan` 接 `tool_payloads`

   - 修 plan / replan / execute payload type

   - 防禦式讀取 `steps`

   - mutable default list 改 `default_factory`
6. `task_service.py`
   - `create_notification()` 補 warning log

### 第二批：補 planner 與 envelope 護欄

1. `tool_plan_service.py`
   - protected keys 規則
   - steps 長度上限
2. `tool_envelopes.py`
   - `Literal[True/False]`

### 第三批：補測試

- [x] 已完成本輪目標測試（2026-06-05）

後端：

1. replan 可保留 `tool_payloads`
2. execute 階段拒絕 `tool_payloads` override
3. handler exception 會被 registry 轉成 failure envelope
4. malformed step 不會直接 KeyError

前端：

1. `plan/replan` payload shape
2. `execute` payload shape 不含 `tool_payloads`

### 第四批：另外立 phase 做 service 權限邊界

1. task 寫入型 service
2. timeline 寫入型 service
3. handler / context actor 注入規則

## 五、驗收條件

完成第一批後，至少要達成：

1. `plan / replan / execute` payload type 與後端行為一致
2. replan 不會靜默遺失前端已準備的工具參數
3. 任一 handler 未包例外時，registry 仍能回傳標準 failure envelope
4. `agent_nodes` 因 step 結構缺漏而 500 的風險下降
5. 通知失敗至少可在 log 中觀察
6. `TaskCreateInput` 不再使用 mutable default list

## 六、這份計畫與後續 phase 的關係

這份計畫不是新 phase 主題，而是：

1. 對 Phase 9.5 已完成主線的收尾補強
2. 為 Phase 9.6 可觀測性與評測基線鋪路
3. 為之後「選項式 Agent」與「更多 tool 接入」先清邊界

最重要的是：

這波不是要證明以前做錯，而是把已經能跑的主線，補到更能擴、更能測、更不容易被未來的自己踩壞。
