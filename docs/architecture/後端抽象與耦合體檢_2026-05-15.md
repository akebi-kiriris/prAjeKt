# 後端抽象與耦合體檢_2026-05-15

## 背景

近期閱讀《Architecture Patterns with Python》第三章「耦合與抽象」時，重新檢視 Learnlink 目前的後端分層狀態。

目前專案已採用接近三層式架構的形式：

- `blueprints/`：HTTP 入口、JWT、request/response。
- `services/`：業務流程、驗證、錯誤轉換、外部服務協調。
- `repositories/`：SQLAlchemy 查詢與資料存取。

這份紀錄的目的不是否定目前架構，而是釐清：現有分層是否真的降低耦合，哪些地方只是「資料夾分開」，但抽象邊界還沒有真正封裝好。

## 整體判斷

目前後端不是單純的雜亂 MVC，已經有不少有效的抽象。

尤其在 RAG / knowledge / timeline 相關功能中，service 多數時候不是直接寫 SQLAlchemy query，而是透過 repository 取得資料。這代表分層不是只有形式，而是已經開始讓資料存取細節集中到 repository。

不過，目前架構還沒有穩定到書中偏好的那種狀態：

- 業務規則可以脫離資料庫測試。
- 外部服務可以透過介面替換。
- transaction 邊界集中管理。
- controller 不需要知道 repository 或權限查詢細節。

比較精準的描述是：

> Learnlink 目前有三層式架構的骨架，也有部分有效抽象；但 service 層仍同時扮演 use case、transaction script、DTO serializer、domain rule、檔案儲存與外部 API orchestration。

## 做得好的地方

### RAG planning 沒有直接碰 ORM query

`backend/services/rag_planning_service.py` 主要透過 repository 取得資料：

- `search_knowledge_chunks_by_text`
- `search_knowledge_chunks_with_scores`
- `get_active_tasks_by_timeline_ids`
- `get_timeline_memberships_for_user`

這是好的方向，因為 RAG planning service 不需要知道 knowledge chunk 或 timeline task 實際怎麼查。

### knowledge repository 有封裝 pgvector 與 fallback 查詢

`backend/repositories/knowledge_repository.py` 已經把以下資料存取細節收進 repository：

- vector distance 查詢。
- text fallback 查詢。
- ready / deleted 狀態篩選。
- personal knowledge 與 project knowledge 的 scope 條件。
- chunk replace / count / document event。

這讓 service 不需要直接理解 pgvector 查詢語法，抽象價值明確。

### task dependency validation 已往 repository 靠

`backend/services/task_service.py` 的 `validate_dependency_task_ids()` 使用 `get_active_task_ids_for_timeline()` 取得同專案任務 ID，而不是直接在 service 裡寫 `Task.query`。

這是正確方向：service 表達規則，repository 處理資料取得。

## 主要問題

### 1. Service 層仍大量知道 transaction 細節

代表檔案：

- `backend/services/knowledge_service.py`
- `backend/services/task_service.py`
- `backend/services/timeline_service.py`

目前 service 裡有大量：

- `db.session.add(...)`
- `db.session.flush()`
- `db.session.commit()`
- `db.session.rollback()`
- `db.session.delete(...)`

這代表 repository 多數時候只封裝了「查詢」，但 transaction boundary 仍散在 service 裡。

短期這是可接受的 transaction script 寫法，但從抽象角度看，缺點是：

- 測試 service 時仍容易綁住 SQLAlchemy session。
- 一個 use case 裡多次 commit，流程中段失敗時比較難推理一致性。
- 未來若想導入 Unit of Work，會需要逐步收斂這些 commit/rollback。

### 2. Service 層直接建立 ORM entity

代表例子：

- `create_task_for_user()` 直接建立 `Task`、`TaskUser`。
- `batch_create_tasks_for_timeline()` 直接建立 `Task`。
- `create_notification()` 直接建立 `Notification`。
- knowledge indexing 流程直接協調 document 狀態與 chunk replace。

這讓 service 對資料模型結構知道很多。

目前不是不能接受，因為 Learnlink 還沒有真正的 domain model 層；但若以抽象為目標，這表示：

- ORM model 變動會直接影響 service。
- 建立資料的規則不集中。
- repository 的角色偏 read repository，而不是完整 persistence abstraction。

### 3. Blueprint 仍有跨層查詢與業務判斷

代表檔案：

- `backend/blueprints/knowledge.py`

目前 knowledge blueprint 直接 import `get_timeline_member`，並在 HTTP handler 中檢查 project membership。

這會讓 controller 層知道「專案檔案區權限」的業務規則。

更理想的方向是：

- Blueprint 只負責解析 request、JWT、query string、回傳 response。
- Service 或 policy helper 負責檢查使用者能不能操作 project knowledge。

### 4. 外部依賴尚未抽象成可替換介面

代表檔案：

- `backend/services/rag_planning_service.py`
- `backend/services/knowledge_service.py`

目前 service 直接建立：

- `GeminiEmbeddingService()`
- `TextSplitterService()`
- `get_default_llm(...)`

這讓測試或替換 provider 時，需要靠 monkeypatch、環境變數或整合測試。

比較符合書中抽象精神的方向是：

- service 函式允許注入 `embedder`、`splitter`、`planner`。
- 預設值仍可用目前實作，避免呼叫端大改。
- 測試時可傳 fake object，讓業務流程不依賴 Gemini / LLM / PDF parser。

### 5. RAG planning service 的職責偏多

`rag_planning_service.py` 目前同時處理：

- payload validation。
- history reference retrieval。
- knowledge reference retrieval。
- embedding fallback。
- project permission validation。
- reference merge / weighting。
- prompt context formatting。
- LLM timeout。
- fallback suggestion。
- response meta 組裝。

這個 service 可讀性尚可，但已經開始接近「一個 use case 裡塞太多細節」。

後續可以拆成幾個小抽象：

- `ReferenceRetriever`
- `KnowledgeReferenceRetriever`
- `HistoryReferenceRetriever`
- `RAGPlanGenerator`
- `ProjectKnowledgePolicy`

不一定要一次拆完，先挑最痛的邊界即可。

## 已觀察到的小 bug

`backend/blueprints/knowledge.py` 中，`batch_delete_knowledge_documents_api()` 與 `batch_reindex_knowledge_documents_api()` 使用 `error_response` 作為區域變數名稱：

```python
project_id, error_response = _require_project_membership(user_id)
```

這會遮蔽原本 import 進來的 `error_response()` 函式。

因此當 `document_ids` 為空時，這段：

```python
return error_response("BAD_REQUEST", "document_ids 必須為非空陣列", 400)
```

可能會變成呼叫 `None`，導致 `NoneType is not callable`。

這個 bug 很適合在重構第一波順手修掉，因為它範圍小、風險低、可以補測試。

## 重構優先順序

### 第一波：knowledge blueprint 權限檢查收斂

目標：

- 修掉 `error_response` 變數遮蔽 bug。
- 把 project membership 檢查從 blueprint 抽到 service/policy。
- 讓 blueprint 不直接 import repository。

預期成果：

- controller 更薄。
- 權限規則集中。
- 測試比較容易覆蓋。

### 第二波：RAG planning 外部依賴注入

目標：

- 讓 `suggest_plan_with_rag()` 可注入 embedder / LLM planner。
- 保留目前預設行為，避免 API 呼叫端大改。
- 測試時不需要真的初始化 Gemini 或 LLM。

預期成果：

- RAG planning service 更容易單元測試。
- provider 替換成本降低。
- 抽象更接近 port / adapter。

### 第三波：RAG reference retrieval 拆分

目標：

- 將 history reference、knowledge reference、merge weighting 分離。
- 讓 `suggest_plan_with_rag()` 更像 use case orchestration。
- 把 retrieval 細節移到獨立 helper/service。

預期成果：

- RAG planning 主流程更清楚。
- reference scoring / fallback 可獨立測試。
- 後續新增來源時不會繼續塞進同一支檔案。

### 第四波：transaction boundary 收斂

目標：

- 先不要全專案導入 Unit of Work。
- 從 knowledge indexing 或 task create 這類高價值流程開始，整理 commit/rollback。
- 逐步避免一個 use case 中出現太多分散 commit。

預期成果：

- 失敗回滾更容易推理。
- service 測試更穩定。
- 未來若導入 Unit of Work，遷移成本較低。

## 暫不急著做的事

### 不急著全面導入 Repository class

目前 repository 採 function-based 寫法，雖然不是書中最典型的 class interface，但在 Learnlink 現階段可讀性還可以。

短期不需要為了「看起來更像書」而全面改成 class。

### 不急著建立完整 domain layer

Learnlink 目前的業務複雜度還沒有到一定要馬上拆 `domain/`、`commands/`、`unit_of_work.py`。

比較務實的方向是：

- 先修明顯跨層。
- 先抽外部依賴。
- 先讓 service 更容易測。
- 等痛點累積後再引入更完整的 domain model。

### 不急著一次搬完所有 db.session

`db.session` 散在 service 裡確實是耦合訊號，但一次全搬很容易爆。

建議採漸進式：

1. 新功能先用較乾淨模式。
2. 修改舊功能時順手收斂。
3. 高風險流程才優先整理 transaction。

## 判斷標準

後續每次重構可以用以下問題自查：

- Blueprint 是否還知道 repository？
- Service 是否能在不連真實外部 API 的情況下測試？
- Service 是否直接知道太多 ORM 建構細節？
- 一個 use case 是否有太多 commit / rollback？
- 權限規則是否散在 controller、service、repository 多處？
- 新增一種 knowledge source 時，是否需要大改主流程？
- 替換 LLM / embedding provider 時，是否只需要替換 adapter？

## 結論

Learnlink 目前已經不是沒有架構的狀態。

真正需要修的不是「有沒有三層」，而是：

> 這三層之間的依賴方向是否穩定，抽象是否真的讓內部細節可以被替換。

目前最值得先處理的是 knowledge / RAG planning 這條線，因為它同時牽涉：

- controller 權限邏輯。
- repository 查詢抽象。
- 外部 embedding / LLM。
- fallback 流程。
- project knowledge scope。

這條線整理好後，可以作為後續 task / timeline / group service 重構的範本。
