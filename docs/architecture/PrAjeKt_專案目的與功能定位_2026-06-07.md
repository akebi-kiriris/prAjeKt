# PrAjeKt 專案目的與功能定位

## 這份文件是拿來做什麼的

這份文件只專注回答兩件事：

1. `PrAjeKt` 這個專案的核心目的到底是什麼
2. 為什麼目前會有這些功能，尤其包含 AI / RAG / Agent

這不是實作紀錄，也不是 phase 規劃文件。  
它比較像是之後整理 README、履歷敘述、面試說法、產品方向時的共同底稿。

---

## 專案原始動機

這個專案最一開始的出發點，不是「我要做一個很炫的 AI 工具」，而是：

> 平常和人合作時，`LINE` 與 `Discord` 很適合聊天，但不太適合真正承接任務、追蹤進度、整理脈絡與保留決策過程。

聊天工具很方便，但也有幾個明顯限制：

1. 訊息容易被洗掉，重要內容難回找
2. 任務、進度、留言、附件、決策常散落在不同對話裡
3. 可以溝通，但不容易形成正式可追蹤的執行流程
4. 小團隊常常不需要很重的大型 PM 工具，但只靠聊天又會越做越亂

所以 `PrAjeKt` 的第一個核心目的，是做出一個：

> 比聊天工具更能承接正式協作流程，但又不要重到像大型企業專案管理系統那樣難上手的協作工具。

---

## 專案想解決的核心問題

`PrAjeKt` 主要想解決的是這個落差：

### 現有聊天工具的優點

1. 即時
2. 好上手
3. 溝通自然
4. 幾乎每個人都會用

### 現有聊天工具的限制

1. 任務不容易正式化
2. 進度不容易追蹤
3. 脈絡不容易整理
4. 文件、討論、決策與執行常彼此斷裂

### `PrAjeKt` 想補上的位置

`PrAjeKt` 想站在「聊天工具」和「正式專案工具」之間：

1. 保留協作時的溝通感
2. 補上任務、時程、留言、檔案、群組、知識整理的正式承接能力
3. 讓個人或小團隊不用切很多工具，也能維持比較完整的專案脈絡

---

## 產品定位

如果要用一句話描述 `PrAjeKt`，目前比較接近：

> 一個給個人與小團隊使用的輕量協作系統，用來承接聊天之外的正式工作流程，包含任務、專案、進度、留言、檔案與知識整理。

它不是單純待辦清單，也不是單純聊天工具，而是偏向：

1. 小型協作管理
2. 任務與時程追蹤
3. 群組脈絡沉澱
4. 專案知識留存

---

## 這個專案的兩層目的

這個專案其實一直有兩層目的，兩者都是真的。

### 第一層：產品目的

產品目的在於解決協作問題：

1. 承接任務
2. 追蹤進度
3. 整理流程
4. 集中專案脈絡

也就是說，這個專案不是為了展示很多技術名詞，而是有一個真實的使用情境：

> 當聊天工具不足以支撐專案執行時，需要一個更正式、但仍然好用的中間工具。

### 第二層：學習目的

這個專案同時也是一個長期技術實驗場，用來練習與整合：

1. Vue
2. TypeScript
3. Python
4. CI/CD
5. Docker
6. 測試
7. 後續的 AI / RAG / Agent 能力

所以它不只是產品原型，也是一個會隨著學習路線逐步擴充的工程實作專案。

## 為什麼會有現在這些功能

### 1. Timeline / Project

專案本身需要一個正式承載單位。  
如果只有聊天訊息和任務列表，很多資訊仍然是散的。

所以需要 timeline / project 這種層級，來承接：

1. 專案名稱與說明
2. 專案時程
3. 任務集合
4. 專案檔案
5. 成員與權限

這是把「聊天中的合作」變成「有邊界的協作單位」的第一步。

### 2. Task / Subtask / Assignment

既然核心問題是聊天工具難以承接任務，那就一定需要：

1. 任務建立與更新
2. 指派與責任歸屬
3. 狀態變化
4. 截止日期
5. 子任務拆分

這些功能不是為了模仿 PM 軟體，而是因為如果少了它們，系統就還是只停留在「可聊天」而不是「可執行」。

### 3. Comments / Attachments

很多真實協作不是只有「做任務」，還包含：

1. 留言討論
2. 補充說明
3. 上傳檔案
4. 保留脈絡

如果任務只是表單欄位而沒有後續討論，實際上很難支撐完整協作。

所以留言與附件存在的目的，是讓任務不只是靜態資料，而是有持續推進的上下文。

### 4. Groups / Realtime Communication

專案合作很多時候還是需要即時互動。  
完全把聊天排除掉，系統會太僵硬。

所以群組與即時通訊的存在，不是回到聊天工具，而是讓：

1. 正式工作流程
2. 即時協作溝通

能在同一個系統內共存。

### 5. Knowledge / File Indexing

專案久了之後，常見問題不是「沒有資訊」，而是：

> 資訊很多，但很難回找、整理與再利用。

所以知識文件與索引功能的目的，是讓專案內容不只存在，而是可以被：

1. 留存
2. 檢索
3. 整理
4. 後續引用

這和單純檔案上傳不同，它更偏向「讓專案脈絡可沉澱」。

## 為什麼會加入 AI / RAG / Agent

這一段最容易被質疑，所以需要特別講清楚。

### 先講結論

AI 不是這個專案的起點，  
但它可以成為這個專案的「脈絡整理與操作加速層」。

也就是說：

> AI 的目的不是炫技，而是降低使用者整理資訊、理解脈絡、操作系統的成本。

---

### 1. RAG 的目的

RAG 在這個專案裡，如果成立，應該是為了解決：

1. 討論太多，使用者很難快速抓到重點
2. 專案文件、留言、知識內容分散，難以引用
3. 使用者需要摘要、建議與脈絡整理時，不想完全手動整理

所以 RAG 的定位不是「因為現在流行所以要加」，而是：

> 讓系統能夠基於專案內既有內容，做出比較有根據的摘要、規劃建議與知識輔助。

---

### 2. Agent 的目的

Agent 在這個專案裡的合理定位，不是取代整個系統，也不是變成一個萬能聊天機器人。

它比較應該是：

> 讓使用者可以用自然語言觸發原本就存在的正式操作流程。

例如：

1. 建立專案
2. 規劃任務
3. 建立任務
4. 更新任務
5. 產生摘要
6. 查詢特定資訊

也就是說，Agent 的價值在於：

1. 降低操作門檻
2. 串接既有工具流程
3. 讓系統從「功能集合」更進一步變成「可以幫忙完成工作流程」

---

## 哪些功能是核心，哪些是延伸

### 核心功能

這些是最直接對應專案原始目的的：

1. 專案 / timeline
2. 任務 / 子任務 / 指派
3. 留言 / 附件
4. 群組 / 基本協作
5. 進度追蹤與狀態流

### 延伸加值功能

這些是建立在核心之上的能力增強：

1. 知識索引
2. RAG 摘要 / 規劃建議
3. Agent 規劃與自然語言操作
4. 風險分析 / AI 任務建議 / group snapshot

這樣的區分很重要，因為可以避免專案目的被 AI 敘事整個蓋掉。

---

## 目前的非目標

為了避免專案目的越來越模糊，目前也可以先明確幾個非目標：

1. 不是要直接和 Jira / Notion / ClickUp 做完整競爭
2. 不是要做成大型企業級流程管理平台
3. 不是為了加 AI 而加 AI
4. 不是把所有聊天行為都搬進系統

這有助於後續做取捨：

如果某個功能很炫，但和核心問題距離很遠，就不一定該優先做。

## 目前可以先採用的一句版說法

### 簡短版

> PrAjeKt 是一個給個人與小團隊使用的輕量協作系統，目的是補上聊天工具在任務承接、進度追蹤與專案脈絡整理上的不足。

### 稍完整版

> PrAjeKt 一開始是因為我覺得 LINE、Discord 很適合聊天，但不太適合真正承接任務、追蹤進度和整理協作流程，所以我想做一個更正式、但又不要太難用的協作系統。後來再逐步加入知識整理、RAG 與 Agent，讓系統不只記錄資訊，也能幫忙整理脈絡、產生建議與降低操作成本。
